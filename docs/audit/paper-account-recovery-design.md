# Paper account persistence and recovery contract

**Status: design only; not implemented, not wired, and not an activation approval.**

## Canonical state that recovery must preserve

The public surface is `GatewayStateSnapshot` in `src/command-gateway.ts`. Recovery must not restore only the visible cash and position array while silently resetting the hidden invariants that govern future commands.

| State | Current owner / mutation path | Recovery contract |
|---|---|---|
| `cashUsd`, `initialPaperCapitalUsd`, `solPriceUsd` | Cash/capital: `setCashUsd`, buy/sell fill branches in `handleSubmitOrder`, `handleSetPaperCapital`. SOL price: default initializer, public `setSolPriceUsd` and `updateSolPriceUsd`, and `requireFreshMarketEvidence` when it accepts validated evidence. `terminal/server.mjs` also calls `updateSolPriceUsd` from its SOL feed loop. | Persist capital in exact integer subunits with explicit conversion/version rules. `solPriceUsd` is a latest quote, not account principal; keep its source, observation timestamp and validity. | Full `positions` | `positions` Map; buy/sell branches in `handleSubmitOrder`; `updatePositionMarks` | Persist every field required to maintain position identity, quantity/decimals, basis and exit policy. Current shape includes asset/pool, mint, symbol, qty, entry, stop, peak, trough, openedAt, costBasisUsd, stage, reconciliationState, tokenDecimals, `lastPeakAt`, `lastMark`, and `lastMarkAt`. Risk extrema/stop are monotone safety state, not decorative UI data. |
| Paper performance | `paperRealizedPnlUsd`, `paperClosedFillCount`, `paperWinningFillCount`, `paperLosingFillCount` | Derive from durable settlements or store a projection that is committed atomically with each settlement. Preserve current code's semantics: each sell fill increments the closed-fill count, and P&L `> 0` increments wins; zero/non-positive increments losses. Do not synthesize historical fills from an aggregate snapshot. |
| `executedIntentIds` | process-local `Set` checked before execution and populated before awaiting the simulator | Durable idempotency keyed by immutable account + generation + economic order ID and command ID. | `pendingBuys`, `inFlight` | process-local maps/sets keyed by pool; populated before `executionEngine.execute`, cleared in `finally` | Persist a reservation/accepted lifecycle record before asynchronous simulation. At restore, no order may simply disappear because the in-memory map is empty. Recover reserved amounts and unresolved order identities or hold the account fail-closed. A zero `inFlightOrdersCount` in a snapshot is only an instant observation and lacks order IDs. |
| Simulator state | `SimulatedEngine` in `src/execution-engine.ts` | It has a mutable PRNG stream, per-pool market-state history, overlays, pending abort controllers, bounded lifecycle audits, and adverse-selection state. `exportState()` currently exports only adverse-selection score and overlays; it does not serialize PRNG position, pool histories, pending work, or lifecycle data. An order report depends on sequential PRNG draws (delay and stochastic drop) and current pool frames. Therefore current simulator state cannot be reconstructed from `GatewayStateSnapshot`, and restarting/replaying an uncheckpointed simulation can yield a different result. |
| Safety/risk control state | `stopEpoch`, `panicClosesInProgress`, `entriesHalted`, `emergencyStop`, automation/mode, `updatePositionMarks` | Restore durable emergency stop before any command/automation admission. Maintain a separate recovery hold that cannot be cleared merely by `CLEAR_EMERGENCY_STOP`. Restore stop epoch/fencing state or establish a new generation epoch that makes all old asynchronous work incapable of committing. Persist peak/trough/last peak and ratcheted stop updates; never lower a saved stop on restart. |
| Reconciliation state | `lastReconciledAt` is initialized to `0`; positions are marked `SIMULATED` | Preserve the value as zero/unknown unless a distinct reconciliation system supplies real evidence. Paper events remain simulations; they never become chain fills, finalized settlement, or live reconciliation facts. |

`GatewayStateSnapshot` also contains `entriesHalted`, `emergencyStop`, `mode`, `automationEnabled`, `reservedCashUsd`, `inFlightOrdersCount`, `stateVersion`, and `operationalMode`. Each field either becomes part of a versioned account/generation projection or is explicitly classified as process-derived and recomputed from durable controls. Do not silently reset it. Configuration used to calculate risk (for example max positions, stop BPS, slippage, freshness, sizing) must be version-pinned or represented in every accepted command's immutable input/evidence; changing config cannot rewrite prior decisions.

`updatePositionMarks()` changes `lastMark`/time, `peak`, `lastPeakAt`, `trough`, and ratchets `stop` upward using `protectiveStop`. Stage 2 must make each safety-relevant watermark change **durable before publish**: compute a proposed watermark transition in a temporary value, atomically append its observation/event and update the canonical position projection, await a confirmed commit, then expose the new values to `tickAutonomousExits()` or any other risk decision. Do not mutate the canonical in-memory position before that commit. On a known pre-commit failure, retain only the last committed in-memory projection and hold risk-increasing commands and stop-dependent automation; the old stop is historical state, not authorization while its risk watermark write is failed. On an unknown commit result, freeze the account until the worker reopens and the exact watermark/projection version is read back. No stop/exit decision may consume either the candidate value or a possibly older durable value while state is ambiguous.

On restore, a persisted mark is historical and **must be stale for authorization purposes**, regardless of its former freshness. Require a new identity-matched, monotonic, fresh quote before using mark-dependent risk decisions. At the same time, retain durable historical peaks/troughs and never recompute a lower stop just because a mark is absent or stale. If a legacy/current code path exposed a candidate watermark before storage completed, or recovery proves the in-memory watermark may be newer than the durable projection, classify that position's risk watermark as `UNKNOWN/UNRESOLVED`; preserve any candidate only as diagnostic evidence. An older, lower stop must not authorize autonomous exits or be presented as the recovered stop. Hold stop-dependent automation and account admission until exact durable evidence is found or an explicitly reviewed conservative repair proves the replacement stop cannot be lower. Do not manufacture a missing peak from the current quote. A persistence failure must not publish the candidate; it retains only last committed memory, holds risk-increasing commands and stop-dependent automation, and marks recovery required. If commit status is ambiguous, freeze and re-read by transaction key/projection version; if exact state cannot be proven, continue the unresolved hold. After process crash, no prior lower stop may authorize protection until this boundary is resolved.

`solPriceUsd` mutation paths need the same provenance boundary. `updateSolPriceUsd` currently accepts any positive finite value; `setSolPriceUsd` is another public setter. `requireFreshMarketEvidence` updates the process-wide SOL/USD cache from validated fresh `PaperEntryEvidence` by default, and `handleSubmitOrder` directly updates that cache from validated exit evidence for autonomous exits. The server guardian loop updates it from a SOL pair only after checking the pair's timestamp is within five seconds, but the current setter stores only the numeric price. For every accepted command, capture one immutable quote record (price, observed-at time, source/evidence identity) from the exact fresh market evidence used to authorize and construct its simulation input. Bind it into the command fingerprint and persist it before execution. Use this same frozen per-command quote for USD-to-lamport amount conversion, simulator pool calibration, fee/tip conversion, proceeds/cost conversion, fallback USD prices, and atomic settlement—even if a fill-time freshness check or the process-wide feed cache observes a newer quote while the simulator is awaited. A newer quote may independently fail the command's drift/freshness gate; it must never silently replace the bound quote mid-command. If there is no valid command-scoped quote, block the command. Persisted results must never be recomputed from a later global SOL/USD cache value after restart.

## Stage 1 storage primitive: what it does and does not provide

The isolated primitive is `PaperLedgerStore` and its worker/schema in `src/platform/storage/paper-ledger.ts`, `paper-ledger-worker.ts`, and `paper-ledger-schema.ts`, with focused checks in `test/platform/paper-ledger-store.test.mjs`. It stores explicit `(accountId,generationId)` scoped generation declarations, command fingerprints, append-only lifecycle events, immutable simulation reports and fills, strict integer amount strings, and unresolved markers. The worker uses WAL + `synchronous=FULL`, serialized transactions, schema-version checks, exact canonical SQL comparison, and a bounded caller queue. It rejects unversioned nonempty databases and same-name altered triggers. Its idempotency only covers the isolated journal operations.

It has no balance/position/performance projection, active-generation pointer, owner/fencing protocol, gateway command result, startup recovery integration, simulator replay contract, or snapshot adoption. `appendFill()` is therefore not a full paper-account settlement transaction. The current state is **isolated storage infrastructure only**, not persistence capability, not account recovery, and not a production-ready paper ledger.

## Required Stage 2 account model

1. **One explicit account identity.** Obtain a stable `paperAccountId` from explicit operator configuration or a durable bootstrap record. Do not infer it from a mint, wallet, environment default, current capital amount, or machine name. Scope every generation, command, reservation, event, fill, projection, stop linkage, and recovery certificate by exact account ID and generation ID.
2. **One explicit active generation.** A durable account row names the active generation and monotonic ownership epoch. A generation has immutable genesis metadata and an append-only state history. Creating another generation does not silently replace the active one. Normal process restarts reload the same generation. A deliberate reset seals the old generation and atomically activates a new generation with explicit opening cash, operator identity, reason, timestamp, and prior-generation reference.
3. **Single canonical writer.** SQLite serializes database writers, but that alone does not make two independent in-memory `CommandGateway` instances safe: the second process can make admission/risk decisions from stale balances and stale positions before reaching SQLite. Acquire an account/generation owner lease under an immediate transaction; include a monotonically increasing fencing epoch in every account-changing write and reject writes from older epochs. Require heartbeat/renewal, orderly drain/release, stale-owner takeover rules, and tests for pause/resume and split-owner races. WAL is local-host only; never place this ledger on a network filesystem. Until the running PID relinquishes ownership through a reviewed handoff, no second terminal may claim its paper account.
4. **Immutable input identity.** Persist the exact canonical normalized command (both incoming command ID and `payload.orderId`/economic intent ID), initiator, normalized side/amount/decimals, evidence IDs + observation times + source/provenance, config/policy version, simulation model/version/seed, and fingerprint before awaiting any simulation. Reuse of any key with a different canonical economic request is a conflict. Duplicate deliveries after commit return the original result, never a fresh simulation.
5. **Write-ahead lifecycle and reservation.** In one transaction insert accepted command + risk/cash reservation + lifecycle event. Before simulation, the account projection reflects the reservation and positions remain unchanged. A sell reserves the exact source position quantity/lot slice. Entry limits, available cash, max-position count, and concurrent per-pool exclusivity are checked against the canonical generation inside the same writer/owner fence; no unlocked read-then-write path can overspend.
6. **Recoverable simulation checkpoint.** Persist the exact simulation request and complete market state used, plus model/build/version and PRNG seed, before calling or before accepting a report. Then checkpoint the complete `FillReport`, telemetry, stage history, evidence references, and a report fingerprint. Either implement deterministic per-order simulation independent of process-global RNG, or never replay a simulation automatically. The minimum safe policy for an `ACCEPTED` command without a durable report is `UNRESOLVED`: keep its risk reservation/account hold and require explicit reviewed resolution. A stored `SIMULATED` report can be settled from its immutable bytes without running the simulator again.
7. **Atomic settlement + projection.** In one SQLite transaction append the terminal settlement/fill and command response; apply exact cash delta, token/position lot delta, basis/fees, realized P&L, fill counters, and release reservation; update position risk marks only under defined monotonic rules; append a projection version/hash and settlement event/outbox item. On commit acknowledgment loss, reopen/query by the unique command/order key and fingerprint. Never apply the same cash or tokens twice. If the caller cannot establish whether commit happened, block account mutations until the row and projection are re-read. In-memory gateway state is updated from committed projection only; a storage exception must never return an optimistic success.
8. **Exact accounting compatibility.** Paper simulator already reports input/output as `bigint`, but the gateway converts USD, quantity, costs, and marks through JavaScript `number`. Stage 2 must define a fixed-point scale and rounding policy for USD, prices, quantities, fees, and basis; preserve token `decimals`; check conservation and overflow; and provide old-vs-new differential cases. Do not claim lamport-exactness for legacy USD-double state. The dashboard may project numbers after durable exact arithmetic; rounded display values are not journal source values.
9. **Derived-learning side effects.** `globalTradeLearningService.recordClosedTrade` is best-effort and outside the gateway's account settlement transaction. A future design should emit an idempotent outbox row within settlement and deliver learning events separately, so a crash cannot create duplicate learning credit or block the canonical ledger. Learning outages must not roll back settled paper account state.
10. **Generation reset/capital semantics.** `setCashUsd(configuredCapital)` must be replaced by: initialize only if no account/generation exists, otherwise load persisted cash and surface config mismatch. `SET_PAPER_CAPITAL` without reset currently changes cash directly; durable semantics require a separate explicit capital-adjustment event with operator reason and exact delta, or rejection if no approved adjustment authority exists. `resetPositions:true` currently clears positions, reservations, in-flight state, performance, and re-baselines capital; it must not delete exposure/history. Require no in-flight or unresolved intents and no open positions before rollover, unless a separately reviewed close/abandon accounting procedure is approved. Archive the former generation read-only; never reuse its IDs or erase history.

## Startup, stop, and failure contract

Startup sequence for any future integration:

1. Bind to the expected project data directory and open the ledger worker. Refuse foreign/unversioned/unrecognized schema, unsupported SQLite runtime, invalid account/generation identity, integrity/FK violations, or WAL/FULL durability capability mismatch. A v1-to-v2 migration is non-destructive, transactional, versioned and verified; it never rewrites unknown schema.
2. Claim the account writer lease/fencing epoch; reject a live/valid prior owner. Resolve any ambiguous stale owner only using an explicit fencing/takeover protocol, never a PID guess or timeout-only heuristic.
3. Load active generation genesis, projection, immutable command/fill chain and projection hashes. Verify arithmetic/conservation, fills-to-projection counts, generation identity, every outstanding reservation and incomplete lifecycle. Mark commands without durable result evidence unresolved; do not silently discard them or execute again.
4. Load the emergency-stop record using existing `EmergencyStopStore` and restore its latch before any user command or automation can be accepted. A malformed/unreadable stop file or failed ledger bootstrap means terminal remains unavailable/entry-halted; it does not clear, replace or bypass the store. The independent stop JSON and ledger database are not one atomic cross-file transaction. Keep the stop latch stronger than account readiness, and make stop clearing require both the existing explicit confirmation semantics and a healthy, resolved account recovery state.
5. Restore verified account projection and every stop/risk watermark, create a separate `RECOVERY_HOLD`, invalidate market freshness, reset in-flight counts only after classifying their durable records, and keep automation disabled. New entries remain denied. If positions are restored, protection/reduction can become available only when fresh market evidence is available and account ownership is held; no stale `lastMark` is used as current authorization.
6. Only after all gates succeed may routes/listener, guardian intervals, and command admission start. Readiness must include `ledgerState`, account/generation, owner epoch, last committed projection version, unresolved command count, and failure reason. The read model may claim `persist READY` only after a running-path test proves these same invariants; a successful SQLite open or a persisted stop does not qualify.

Worker error and commit ambiguity are distinct. A worker startup/schema error prevents startup. A bounded queue rejection occurs before the operation is accepted. A worker exit or lost response during/after `COMMIT` has unknown outcome; reopen a fresh worker and query the unique transaction key before retrying. If that query cannot prove committed vs absent state, freeze risk-increasing commands and hold recovery; never infer rollback from missing acknowledgment. Keep all accepted events and SQLite WAL state together in backup/restore; copying only the main `.sqlite` file while WAL is live can omit committed transactions. Use SQLite's online backup/checkpoint mechanisms with a quiescent/verified boundary, and verify restored integrity and projection hashes before use.

The emergency-stop implementation is intentionally separate and has its own explicit limitations: it does not provide paper balance persistence, power-loss guarantees for arbitrary filesystems, cross-process ownership, or one atomic transaction with an account ledger. This design does not change that interface. It adds no signer, signature, send/broadcast, live mode, or chain settlement capability; `CommandGateway` remains paper-only.

## Crash and adversarial verification matrix

Every row below needs a subprocess/worker crash test using the actual store/gateway path, deterministic assertions on both disk and restarted memory, and a ledger consistency check. Existing unit tests and a mocked thrown exception alone do not certify process death at every commit boundary.

| Fault point | Required restart result |
|---|---|
| Before generation/genesis commit | No active generation; no default account silently created from current capital. |
| After genesis commit, before acknowledgment | Query returns that exact generation once; retry cannot create a second active generation. |
| Before accepted-command/reservation commit | No accepted command or reservation; command has no execution effect. |
| After accepted reservation commit, before simulator starts | Reservation/identity restored; command is unresolved/held unless exact deterministic replay contract proves safe. No automatic duplicate execution. |
| Simulator running / cancellation racing emergency stop | After restart, durable stop is restored, automation off, no in-flight simulation assumed alive. A late old-owner completion is fenced out. |
| Simulator returned, report write not committed | If no checkpoint is present, unresolved; do not infer fill from in-memory result or synthetic signature. |
| Report checkpoint committed, settlement not begun | Restore `SIMULATED`, then settle only from exact durable report; no simulator replay. |
| During atomic fill+projection before commit | Either all fill/projection/counters/reservation release are absent, or all are present; never partial. |
| Commit completed, acknowledgment lost | Query returns exact same result and balances; retry performs no second fill or counter change. |
| Projection committed, in-memory projection not refreshed | Restart equals committed projection; running caller fails closed until it reloads/compares state version. |
| Duplicate same command/order and same fingerprint, concurrent workers | One accepted operation/result; loser sees stored result. |
| Duplicate key with changed request/report/fill/reason/timestamp | Deterministic conflict; immutable original event survives. |
| Generation reset races order/mark/stop or another process | Old epoch cannot commit after fence; former generation remains complete and immutable; no balance/exposure disappears. |
| Stop save/clear fails or races panic close | Existing stop semantics remain fail-closed; do not claim coordinated atomicity with paper ledger. Existing stop crash tests remain required. |
| Freshness expires during restart; time moves backward/future mark | Last mark is historical only; exits requiring fresh evidence are blocked; extrema and stop never loosen. |
| Stop/peak/trough update is interrupted before, during, or after its durable commit; duplicate or out-of-order mark arrives | No risk consumer sees a watermark before its commit. After an unknown commit, re-read projection version; if the durable value may be lower than the lost in-memory value, mark watermark unresolved and block stop-dependent exits until verified repair. Older/stale/future observations cannot overwrite mark time, lower extrema, or loosen stop. |
| Mark commit fails before commit vs. commit acknowledgment is lost; mark candidate was or was not exposed | Known pre-commit failure retains only last committed memory and blocks stop-dependent automation; ambiguous outcome freezes and re-reads exact event/projection. If legacy code may have exposed the candidate, mark risk watermark unresolved; no older/lower stop authorizes an exit until verified or explicitly repaired. |
| SOL/USD feed updates while a command awaits simulator completion | Durable order input/result stays bound to one captured quote and timestamp for amount, fee and proceeds conversion. A later feed quote cannot change that command's economics; policy may reject on drift, and the new feed value applies only to later commands. |
| Corrupt/truncated DB, altered trigger/table/index, wrong `user_version`, FK failure, non-WAL, queue overload, worker crash | No listener/readiness; original DB/WAL preserved; no auto-reset/recreate/import. |
| Backup with live WAL and restore to disposable DB | Backup includes committed WAL transactions, validates schema, FK/integrity, event chain, projection and active generation before use. |

Focused existing tests that must be retained and extended: `test/platform/paper-ledger-store.test.mjs` (isolated journal scoping, idempotency, worker race, restart unresolved, schema tamper and DDL rollback); `test/paper-stop-persistence.test.mjs` and `test/paper-emergency-stop.test.mjs` (separate stop semantics); `test/paper-evidence-honesty.test.mjs` (different `Engine` path; no proof for the terminal gateway); gateway execution/idempotency tests in `test/command-gateway-and-axiom.test.mjs`; and stale-mark/autonomous exit tests such as `test/autonomous-exit-freshness.test.mjs`. Add a gateway-level test that crashes immediately before and after a risk-watermark commit, reopens the store, then proves a lower saved stop cannot authorize an exit while the watermark is unresolved; in the same test family inject older, stale, and future-mark observations and prove none overwrite the committed watermark. These process-death and out-of-order stale-mark tests are mandatory before changing startup. Add gateway projection differential tests as well. Re-run complete `npm test` and terminal tests after integration; focused green alone is not release evidence.

## Explicit non-claims and blockers

- No durable gateway account state or current account recovery exists today. The Stage 3 marker migration and offline kernel prototype do not change this.
- Stage 1 journal rows do not reconstruct `GatewayStateSnapshot` and do not make `persist` ready.
- The `Engine` recovery tests in `test/paper-evidence-honesty.test.mjs` address another composition root.
- A fresh hash, HTTP 200, zero observed in-flight count, WAL/FULL mode, green unit suite, or persisted emergency stop does not prove a consistent account checkpoint.
- WAL/FULL durability relies on SQLite/VFS/filesystem behavior; actual deployment filesystem and power-failure behavior require testing. Node's `node:sqlite` is a release-candidate API on supported Node 24 documentation; the exact runtime/SQLite versions must be pinned and tested.
- Account writer fencing, full projection, deterministic or conservative simulator crash policy, current position mark treatment, capital reset authorization, and genuine process-kill recovery tests are outstanding. The prototype has no persistence or admission path and must not be described as recovery-capable.
- The changing active PID 29744, its live balances/position/automation, and all adoption or handoff actions remain untouched and unavailable to this implementation until separate explicit operator approval and final review.
- No signer, live order, broadcast, chain settlement, or mainnet truth is introduced. Paper simulation remains explicitly non-chain evidence.

## Technical sources

- The repository requires Node `>=24` in `package.json`; current [Node.js v24 SQLite documentation](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html) identifies `DatabaseSync` as synchronous and the `node:sqlite` API as Stability 1.2 / Release Candidate. SQLite work should stay off the terminal event loop in its worker thread, with the exact Node/runtime matrix tested.
- [SQLite synchronous pragma](https://sqlite.org/pragma.html#pragma_synchronous) documents WAL + `synchronous=FULL` durability behavior and its dependence on the VFS sync operation. This supports a chosen durability mode, not proof about the actual machine's storage hardware.
- [SQLite write-ahead logging](https://www.sqlite.org/wal.html) describes one writer at a time, local-host shared-memory requirements, checkpointing, and the persistent `-wal` file. This is why a process-level account owner/fencing protocol is still necessary and a live backup cannot be a copy of only the main database file.
- [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html) describes all-or-none transaction behavior under SQLite's documented operating assumptions. An application still has to resolve a lost commit acknowledgment by querying durable idempotency keys rather than guessing.
