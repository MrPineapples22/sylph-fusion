# Canonical paper-account v2 schema and domain specification

**Status: critical design specification only. No canonical v2 implementation exists.** Independent review rejected the earlier partial account-projection implementation. Current code contains only the legacy v1 command/fill journal, an inert SQLite `user_version=2` prototype marker, and a nonpersistent reducer prototype. Those artifacts cannot restore `CommandGateway`, authorize admission, or support account recovery. This specifies a future canonical design; it does not authorize live integration, process changes, or snapshot adoption.

This follows the accepted Stage 2 recovery contract and accepted v2 implementation proposal, while resolving the independent review findings: settlement must consume one exact durable simulator report; unresolved execution cannot replay; state must represent full per-pool/lot accounting and every safety watermark; ownership fencing must be a DB-checked lease/epoch rather than a positive-integer assertion.

## 1. Goals and hard boundaries

The database must rebuild the complete paper-only account state from immutable genesis and events, without consulting a live process snapshot, current environment capital, the global quote cache, or a restarted simulator. A projection snapshot is a verified cache of that fold, never independent authority.

The design remains simulator-only. It creates no signing, RPC broadcast, Jito submission, wallet, chain settlement, or reconciliation authority. Rows and APIs use `SIMULATED` / `PAPER` terms. `lastReconciledAt` remains zero/unknown unless a separate evidence-backed reconciliation system is designed; a paper fill cannot set it.

The active PID 29744 observation and preserved JSON snapshots are audit observations only. No bytes from them may seed genesis. A future operator-attested genesis requires a separately approved frozen handoff and must label aggregate historical data unverified; it cannot invent fill rows or simulator lineage.

## 3. Versioning and table namespaces

The logical domain format is **paper-account model v2**. SQLite `PRAGMA user_version` for the canonical implementation must be **3**, because version 2 is already occupied by the inert prototype marker. Never reinterpret or replace that schema under the same version number.

All future canonical tables use the `pa2_` prefix, leaving Stage 1 v1 tables byte-for-byte intact. SQLite uses `STRICT` tables. Amounts that can exceed SQLite signed integer or JavaScript safe integer range are canonical decimal `TEXT`; `INTEGER` is only for bounded timestamps, epochs, counts and sequences. Genesis, event payloads, requests, evidence, reports and projections use the exact canonical codec defined below; all hashes are over exact stored bytes.

### 3.1 Canonical byte encoding and hash preimages

Canonical codec identifier is `SYLPH-JCS-1`. It applies [RFC 8785 JCS](https://www.rfc-editor.org/rfc/rfc8785.html) to the following restricted JSON data model. Each canonical JSON document (genesis, event payload, request, evidence, report, telemetry, result, or projection) is limited to 1,048,576 UTF-8 bytes. Container nesting depth is at most 64, counting a top-level object/array as depth 1 and incrementing only when entering a nested object/array; scalar children do not add depth. The byte limit is checked on raw input before UTF-8 decoding/parsing and incrementally while serializing before output allocation exceeds the cap; the depth limit is checked before descending into a nested container. These bounds apply recursively at every ingress and are part of codec version 1. The restricted JSON data model is: top-level values are objects; allowed values are null, booleans, strings, arrays, objects, and safe-integer numbers only. Numeric values must be finite integers in `[-9007199254740991,9007199254740991]`, with negative zero forbidden; larger integer magnitudes and every financial quantity are JSON strings containing canonical base-10 integer lexemes. Canonical stored JSON has no BOM, whitespace, trailing bytes, or alternate number/string escapes. UTF-8 decoding is fatal on malformed sequences. Reject duplicate object member names before ordinary JSON parsing, unpaired UTF-16 surrogates, accessors, sparse arrays, extra array properties, non-plain object prototypes, and Node-detectable proxies (`util.types.isProxy`). For every object recursively, accept only exact `Object.prototype` objects with own enumerable string-keyed data properties: reject every own symbol key, non-enumerable string property, accessor, or inherited-property dependency; consumers read fields only from own properties. Arrays must have exact `Array.prototype`, a dense sequence of own enumerable data properties for canonical indices `0..length-1`, and only the intrinsic non-enumerable `length` in addition; reject symbols, holes, accessors, non-enumerable indices, and any extra own keys. Apply these shape checks at all ingress before fingerprinting, not only at a later consumer. Object member names are recursively sorted by unsigned UTF-16 code-unit lexicographic order as RFC 8785 specifies; array order is preserved. String escaping and integer serialization follow RFC 8785/ECMAScript exactly. Unicode normalization is never performed: canonically equivalent NFC/NFD strings remain different values and different bytes. A parsed byte payload is accepted only if strict duplicate-aware parsing followed by `SYLPH-JCS-1` serialization reproduces the exact original bytes. Codec version is included in immutable genesis policy hashes and is never silently upgraded during replay.

For hash framing, `LP32(s) = U32BE(byte_length(UTF8(s))) || UTF8(s)`, where the prefix is unsigned 32-bit big-endian and length is measured in bytes. Every framed identifier/type string is valid Unicode scalar text, UTF-8 encoded without normalization, and limited to 4096 bytes. `U64BE(n)` is unsigned 64-bit big-endian; values must fit both SQLite signed INTEGER and the JavaScript safe-integer range before encoding. Hash bytes are raw 32-byte SHA-256 values, not lowercase hex text.

`genesis_sha256 = SHA256(ASCII("SYLPH-PAPER-ACCOUNT-GENESIS-V2") || 0x00 || U32BE(genesis_json_byte_length) || genesis_json_exact_bytes)`. `payload_sha256 = SHA256(payload_exact_bytes)`. `event_sha256` preimage is, in this exact order: `ASCII("SYLPH-PAPER-ACCOUNT-EVENT-V2") || 0x00 || LP32(account_id) || LP32(generation_id) || LP32(event_id) || LP32(event_type) || U64BE(payload_version) || U64BE(account_sequence) || U64BE(generation_sequence) || U64BE(owner_epoch) || U64BE(occurred_at_ms) || U64BE(recorded_at_ms) || payload_sha256_raw32 || previous_event_sha256_raw32`. The first account event uses 32 zero bytes for `previous_event_sha256`. Hash encoding version is immutable for a database and a different encoding requires a new model/schema version plus an explicit migration.

## 4. Canonical tables

The following is the normative logical field contract. Exact SQL, checks, trigger text and indexes require independent review before implementation.

### `pa2_accounts` - control and single-writer fence

- `account_id TEXT PRIMARY KEY`; `active_generation_id TEXT NULL`; `admission_state` in `BLOCKED`, `RECOVERY_HOLD`, `READY`, `STOPPED`, `SEALED`.
- `owner_id`, `owner_epoch INTEGER >= 0`, `lease_id`, `lease_until_ms`, `lease_renewed_at_ms`. Lease fields are wholly null or complete; epoch starts at zero for blocked bootstrap, increments exactly once on each successful acquisition/takeover, never changes on renewal/release, and never resets across generations.
- Every account-changing `BEGIN IMMEDIATE` transaction verifies account, active generation, owner ID, lease ID, epoch, held process-lock identity and unexpired lease before appending. Recovery takes the same-host OS process lock, performs a read-only validation pass with no owner lease, then separately acquires a DB-fenced owner only after all gates pass. The OS lock serializes process lifecycle; the DB epoch fences stale writers; neither alone substitutes for the other.
- Before a positive-epoch owner is acquired, any recovery, clock, lock, stop-store or integrity uncertainty is a process-local deny hold under the retained exclusive OS lock: perform no account-table mutation, event append, lease update, or admission change. The durable `admission_state` remains its last committed value, but is not readiness evidence; the process must keep listeners, automation and command admission disabled. Runtime health exposes `processRecoveryHold=true` and a reason. Clear this in-memory hold only after a fresh complete read-only validation succeeds. Once ownership and the event prefix are fully valid, a separately defined positive-epoch `RECOVERY_HOLD` event may durably record a known hold; never attempt that write when clock/lease/lock integrity is uncertain.
- Epochs and persisted lease timestamps must remain within JavaScript safe-integer and SQLite signed-integer bounds; if `owner_epoch >= Number.MAX_SAFE_INTEGER` or adding the configured TTL would overflow, refuse acquisition/renewal and remain held. Never wrap, saturate or reset an epoch.
- Lease clock contract: `lease_until_ms` and `lease_renewed_at_ms` are safe-integer UTC Unix milliseconds. The genesis-pinned runtime policy is `{leaseDurationMs:30000,renewalDueMs:10000,maxWallMonotonicSkewMs:1000,maxClockUncertaintyMs:1000,requireSynchronizedClock:true}`. Every owner event carries an exact `clockObservation` object `{bootId,monotonicNanoseconds,sourceId,synchronized,uncertaintyMs,wallUnixMs}`; `monotonicNanoseconds` is canonical unsigned decimal text, `wallUnixMs` is a safe integer, and the clock-health adapter must attest `synchronized=true` and uncertainty <=1,000 ms. `bootId`/`sourceId` come from a deployment-approved OS clock-health adapter, not request data. In a running process, compare wall-clock elapsed time with `process.hrtime.bigint()` elapsed time and tolerate at most 1,000 ms discrepancy. A backward wall-clock step, >1,000 ms discrepancy, missing/unsynchronized clock health, non-increasing renewal time, or expired lease causes immediate `RECOVERY_HOLD`; no operation extends an expired lease. After a crash, a new process must hold the OS lock and require `wallUnixMs-uncertaintyMs >= persisted lease_until_ms` plus synchronized clock health before takeover. If the platform cannot provide this evidence, ownership remains unavailable. The same process must still hold the lock during every write. Clock/lock uncertainty is never repaired by increasing expiry.
- Process-lock identity is a canonical object `{hostId,lockNonce,pid,processStartToken}`: stable opaque host ID, random UUID lock nonce, positive safe-integer PID and OS-derived process-start token (PID alone is insufficient). Each transaction proves it still owns that exact lock. A new process creates a new nonce; lock acquisition never itself authorizes activation or readiness.

### `pa2_generations` - explicit immutable genesis

Primary key `(account_id,generation_id)`.

- Immutable `genesis_json BLOB`, `genesis_sha256`, schema version, created time/operator, reason, prior generation, origin and exact policy/config/simulator hashes.
- Fixed-unit `initial_capital_usd_micro`, `opening_cash_usd_micro`, `initial_cash_available_usd_micro`. Any difference is explicit genesis data.
- Pin accounting, risk, config, conversion, simulator build/report schema and token-metadata policy versions.
- The exact runtime configuration bytes committed by `configHash` must include the owner lease/clock policy above. These are explicit policy values, not environment defaults; genesis/config verification refuses missing, changed or runtime-overridden values. Owner events record `leaseDurationMs` and `clockObservation`; the fold checks them against genesis config, while the renewal scheduler enforces configured renewal and clock-skew bounds. A future different duration requires a new reviewed config/genesis contract and crash/clock tests.
- State is `PENDING`, `ACTIVE`, or `SEALED`; transitions require append-only control events. This specification permits only `EXPLICIT_OPERATOR_GENESIS`. `ATTESTED_GENESIS`, active-account adoption, and snapshot/process-state adoption are disabled pending a distinct reviewed contract and are refused by bootstrap/activation. Never infer genesis from v1, environment, `paper.json`, live process, or snapshot.

### `pa2_events` - authoritative append-only journal

- Primary key `(account_id,event_id)`; `event_id` is a canonical UUID string unique within account. Fields include non-null `generation_id`, account-global contiguous `account_sequence`, per-generation contiguous `generation_sequence`, `event_type`, payload version, optional command ID, owner epoch, occurred/recorded times, exact canonical payload bytes, payload SHA-256, previous account-event hash and event hash. Enforce unique `(account_id,account_sequence)` and `(account_id,generation_id,generation_sequence)`, with foreign keys to account/generation. No NULL or reserved-sentinel generation scope is allowed.
- `account_sequence` is the single total order across every generation in an account; `generation_sequence` is a contiguous local order. A single per-account hash chain follows `account_sequence` across generation boundaries; both sequence values are included in each event hash. On each generation, the first event uses `generation_sequence=1`. Wall-clock fields never order facts.
- Event hash is SHA-256 over ASCII `SYLPH-PAPER-ACCOUNT-EVENT-V2\0`; then length-prefixed UTF-8 account ID, generation ID, event ID and event type; then payload version, account sequence, generation sequence, owner epoch, occurred time and recorded time as unsigned 64-bit big-endian integers; then 32 raw bytes of payload SHA-256 and 32 raw bytes of previous-account-event SHA-256. Reject overflow and noncanonical UTF-8. Genesis hash is SHA-256 over domain separator `SYLPH-PAPER-ACCOUNT-GENESIS-V2\0` and exact canonical genesis bytes. `GENERATION_CREATED` payload commits to that genesis hash; its event and `pa2_generations.genesis_json` are verified as a pair.
- Bootstrap `ACCOUNT_BOOTSTRAPPED` and `GENERATION_CREATED` events are both scoped to the stable account ID and newly specified generation ID. Within one immediate transaction, insert blocked account + pending generation/genesis, then append `ACCOUNT_BOOTSTRAPPED` at account sequence 1 / generation sequence 1 / owner epoch 0, followed by `GENERATION_CREATED` at account sequence 2 / generation sequence 2 / owner epoch 0. The first event proves account bootstrap identity/fingerprint; the second commits the immutable genesis hash and initializes the generation fold. Both rows and both events commit or roll back together, so no observable partial genesis exists. `owner_epoch=0` is valid only for these two bootstrap event types; all other account-changing events require a verified positive owner epoch.
- Same event ID + identical fingerprint is exact retry; changed bytes conflict; old sequence replay fails. UPDATE/DELETE triggers reject mutation. No REPLACE or raw SQL write API.

### `pa2_commands` - immutable request identity and result index

- PK `(account_id,generation_id,command_id)`; unique `(account_id,generation_id,economic_order_id)`. Derive `economic_order_id` only from the exact parsed canonical `request_bytes` under the orderId normalization contract in §5; never accept a caller-supplied row/event value that disagrees.
- Store immutable initiator/type/pool/mint/side/decimals, normalized request bytes/hash, config/risk hashes, accepted evidence bytes/hash, frozen quote, acceptance sequence and exact amount units.
- Status is derived from events: `ACCEPTED`, `SIMULATED`, `SETTLED`, `REJECTED`, `UNRESOLVED`, `CANCELLED_BEFORE_SIMULATION`, `MANUALLY_RESOLVED`. It is not separate authority.
- Store exact terminal `CommandResult` bytes/hash so retries return original result/stateVersion. Reuse of either ID with changed request/evidence conflicts.

### `pa2_simulation_reports` - immutable checkpoint

- PK `(account_id,generation_id,command_id)`. Store exact canonical simulator request bytes/hash, exact report bytes/hash, telemetry bytes/hash, report schema/build, seed identity and recorded time. This table intentionally has no report-status column; status is derived only by strict parsing of the exact report BLOB under the pinned report schema.
- `execPrice` is a decimal string encoding of a finite source JS number under shared conversion `SYLPH-F64-DECIMAL-1`: reject NaN, infinities and negative zero; begin with ECMAScript `Number.prototype.toString()` shortest round-trip output, parse sign/coefficient/optional exponent, move the decimal point by the exponent to produce plain non-exponential base-10 notation, add leading/trailing zeroes as needed, and remove only redundant fractional trailing zeroes and a now-empty decimal point. Preserve the sign for nonzero values; zero is exactly `"0"`. Parsing the resulting decimal string back to Number MUST reproduce the original finite value exactly, and re-running this algorithm MUST return the identical string. This shared conversion is pinned by `fill-report-v1` and `telemetry-v1`; changing it requires a new corresponding schema version.

The optional `failureReason`, when present, is exactly one of `SLIPPAGE_EXCEEDED`, `AUCTION_LOST`, `STALE_STATE`, `PRE_TRADE_RISK_REJECTED`, or `CIRCUIT_BREAKER_HALTED`; it is absent for reports that have no failure reason, never null. Optional `currentStage`, when present, is exactly one of `IDLE`, `VALIDATING`, `QUOTING`, `SIGNING`, `SUBMITTING`, `SETTLED`, `REJECTED`, `EXPIRED`, or `FAILED`; it is absent when undefined, never null. `lifecycleHistory` is deliberately excluded from this canonical accounting report object and MUST NOT appear in its bytes. `StageTransitionRecord.metadata?: Record<string, unknown>` is open-ended and therefore is not safe to treat as canonical report/accounting evidence; if retained for diagnostics it requires a separate bounded, versioned non-authoritative format and is excluded from report hash, status decision and settlement. Report schema/build/seed are row/event/genesis context, not fields claimed to exist in `FillReport`.

`telemetry_bytes` is a closed SYLPH-JCS-1 object with exact envelope keys `{schema,telemetry}` and exact `schema="telemetry-v1"`; `telemetry` has exactly `{engineMode,simulatedSlotLagMs,priceImpactPct,preTradeReserves,postTradeReserves}` as defined by the `Telemetry` interface in `src/execution-engine.ts`. `engineMode` is exactly `PAPER` or `LIVE_JITO_QUIC`. `simulatedSlotLagMs` is a finite nonnegative source number encoded as a string by `SYLPH-F64-DECIMAL-1`; `priceImpactPct` is likewise finite, nonnegative, and encoded by the same helper in percent units. Both reject negative zero; zero is exactly `"0"`. No extra range cap is imposed beyond finite source-number representability and the 1 MiB canonical-document limit. Each reserves object has exactly `{sol,token}`; both values are nonnegative BigInt encoded as canonical unsigned base-10 strings, bounded by that same canonical-document byte limit (zero reserves are permitted for rejected/fallback telemetry). The versioned parser rejects unknown/duplicate/missing keys, nulls, wrong types, noncanonical decimals/integers, malformed UTF-8, and any noncanonical/trailing bytes. The complete exact envelope bytes are stored in `telemetry_bytes`; `telemetrySha256` in `SIMULATED` and `telemetry_sha256` in `pa2_simulation_reports` both equal SHA-256 of those exact bytes. No open metadata is accepted.
- Report and `SIMULATED` event commit together before settlement. Settlement references exact report hash. A command accepts only one report. No replay to generate another.

### `pa2_reservations` - open-risk projection

- PK by account/generation/command. Fields: kind (`BUY_CASH`, `SELL_POSITION`, `FEE_BUFFER`), USD-micro cash, optional exact lot ID, token raw quantity, fee-buffer lamports, creating sequence and `OPEN`, `RELEASED`, `CONSUMED`, `UNRESOLVED_HOLD` state.
- Created atomically with `COMMAND_ACCEPTED`. A sell reserves an exact source lot/quantity. Release or consume only atomically with a durable reject, settlement, or a proven pre-simulation cancellation. An unresolved reservation remains held even after manual cancellation resolution; capacity checks include every non-released reservation.

### `pa2_position_lots` - full per-fill position state

- PK `(account_id,generation_id,position_lot_id)`; immutable lot ID unique; opened fill reference. Identity: pool, mint, symbol, side (`LONG` currently), token program if known, decimals, opening command/fill, open time.
- Quantities `opened_qty_raw`, `remaining_qty_raw`, `closed_qty_raw`; invariant opened = remaining + closed.
- Basis fields: opening/remaining/closed USD micro, entry fees and fee-conversion evidence. Invariant opened basis = remaining + closed under exact integer remainder rule.
- Preserve entry micro-USD/token, stage, entry policy hash/reason, exit-policy state; `reconciliation_state='SIMULATED'` until a separate evidence design exists.
- Allow multiple lots for one mint and multiple pools. Current Gateway's one-position-per-pool map is only an adapter/display constraint; canonical storage does not merge lots.

### `pa2_risk_watermarks` - committed safety state

- PK by account/generation/lot. Fields: status (`KNOWN`, `STALE`, `UNKNOWN_UNRESOLVED`, `REPAIR_HOLD`), exact last mark, observation/record times, source/evidence ID+hash/sequence, peak/time, trough/time, protective stop, policy hash, last event sequence.
- A risk observation event carries evidence identity, sequence, times, policy hash and exact mark. Reducer accepts only fresh, identity-matched, ordered marks. Older/stale/future/equal-time ambiguous marks remain auditable but cannot replace current mark.
- `peak=max(old,mark)`, `trough=min(old,mark)`, stop=`max(old, protectiveStop(entry,peak,pinnedPolicy))`. None regress. On restore, last mark is stale; retain extrema/stop but require new fresh quote before market-dependent exits.
- Watermark is durable-before-publish. Known precommit failure holds risk consumers; unknown commit freezes/rereads exact event/hash/version. If a candidate might have been exposed, an older lower stop never authorizes an exit until proven or explicitly conservatively repaired.

### `pa2_fills` - immutable simulated accounting facts

- PK by account/generation/fill; unique command if one report is one fill, otherwise command+ordinal. Store command/report hash, side/pool/mint/decimals, integer input/output and units, time/latency, AMM/priority/tip fee components, quote/evidence IDs, exact cash/token deltas, gross/net proceeds, basis closed, realized P&L, trigger, lot references and basis remainder.
- No fill without committed matching report. Rejected/expired report is terminal but no fabricated fill. Buy creates lot; sell consumes only reserved lot. Partial-sell behavior is pinned policy.

### `pa2_projection_snapshots` - verified checkpoint

- PK account/generation; `projection_version`, both `last_account_sequence` and `last_generation_sequence`, matching last event ID/hash, schema version, exact canonical projection bytes/hash, time. A checkpoint is valid only when both coordinates and hash identify the same final event in the verified account-global/per-generation fold; startup recomputes and compares all fields.
- Full state includes identity, initial/current capital, cash, every lot/watermark, realized P&L/fill counters, command idempotency/status/result, reservations/holds, policy hashes, paper/shadow mode, requested automation, entry halt, emergency-stop identity, `stop_epoch`, state version and last committed version. Simulator state is not claimed restorable unless its complete deterministic checkpoint is later proven.
- Update in same transaction as event. Startup recomputes from genesis/events and compares hash/sequence. Rebuild only from complete verified events; mismatch blocks. Snapshot is never genesis.

### `pa2_outbox` and control-event representation

`pa2_outbox` uses unique `(account,generation,event,consumer)`, payload/hash, attempts/status/time. Settlement inserts learning delivery atomically; delivery is idempotent and at-least-once. Learning outages cannot roll back accounting.

There is one authoritative append-only event stream: `pa2_events`. Generation create/activate/seal, owner acquire/renew/release/fence, recovery hold/release, risk repair and stop observations are event types in that stream and share its sequence, hash chain, idempotency and account/generation scope. `pa2_control_events` is only a derived index/view keyed to the authoritative `pa2_events` row; it stores no independent payload or competing truth and is rebuildable. Journal/genesis/report/fill/control facts are append-only. Mutable rows above are projections changed only with a proving event and checkpoint in one immediate transaction. Exact schema verifier covers all SQL objects.

### Event ordering, authority and projection verification

The immutable authority consists of (1) exact canonical `pa2_generations.genesis_json` bytes plus its SHA-256, and (2) the append-only `pa2_events` rows chained by `account_sequence`. Genesis establishes only initial state; every subsequent state transition must be represented by an event. These are not two independent versions: `GENERATION_CREATED` carries the genesis fingerprint/hash and the fold refuses any mismatch. Nothing in mutable projection tables may override the fold.

Every account event has both sequence numbers. `account_sequence` is allocated as `max(account_sequence)+1` under the fenced immediate transaction and never resets across generations. `generation_sequence` is allocated as `max(generation_sequence)+1` for that account/generation and starts at 1. The previous-hash field links to the preceding account-global event (zero hash at account bootstrap), not merely the prior event in the current generation. Generation transitions are ordered in that same chain: the seal payload binds the old generation prefix using both sequence coordinates and its final hash/projection; the seal event is appended next to the old generation; then create/bootstrap the new generation, acquire its owner epoch, and activate it. A checkpoint stores both coordinates and must match exactly one event; it cannot substitute one sequence dimension for the other. Rebuild validates no gaps/duplicates in either sequence, exact hash linkage and epoch transitions before it accepts any projection.

Source-of-truth versus derived rows is explicit: `pa2_accounts` current admission/owner fields, generation state, command status/result indexes, reservations, lots, risk watermarks, fills, report lookup rows, projection snapshots and `pa2_control_events` are materialized projections or indexes. Recompute them from genesis + events; never use them to fill an event gap. `pa2_simulation_reports` may retain exact large request/report/telemetry bytes for retrieval, but the `SIMULATED` event commits their hashes and the report row must exactly match those immutable event-bound bytes. `pa2_fills` and command/result rows similarly must match their source event payloads. `pa2_outbox` is the sole operational exception: its delivery-attempt/status fields are non-accounting delivery state, while immutable payload/hash/unique event identity are derived from the committed source event. The `pa2_control_events` view exposes selected `pa2_events` identifiers, sequences, type, epoch and payload bytes; it is never a separately writable journal. Exact schema verification includes the view SQL.

### Exact command lifecycle event contract (payload version 1)

All command lifecycle events below use `payload_version=1` and a canonical SYLPH-JCS-1 object with exactly the listed keys. `commandId` is a lowercase canonical UUID and MUST equal the non-NULL `pa2_events.command_id` column. The v3 event table has no command foreign key, so the lifecycle fold MUST independently require exactly one scoped `pa2_commands` row for each lifecycle `command_id`; the account/generation/command tuple, not `command_id` alone, is the key. No event may use a payload-only command ID or borrow another command's report/fill. Large immutable request/evidence/quote/report/telemetry bytes live in their defined BLOB columns; event payloads commit their raw-byte SHA-256 hashes and matching metadata so the canonical event remains within its 1 MiB codec bound. Inline evidence/proof/result byte fields use canonical unpadded base64url (`*BytesB64url`) and companion lowercase-hex `*Sha256=SHA256(decoded exact bytes)`. A report's embedded status is one of `FILLED`, `REJECTED`, or `EXPIRED` and MUST be obtained from strict parsing of its exact bytes, not a separate mutable/status column. Event IDs remain unique journal identities; command lifecycle idempotency is by command ID plus the accepted request fingerprint, not by appending duplicate lifecycle events.

The exact stored `pa2_commands.request_bytes` is the canonical serialized `SubmitOrderCommand.payload` object accepted by the writer. Parse it strictly and derive `economicOrderId` deterministically: if own property `orderId` is absent or is the empty string, use the event's `commandId`; if it is a non-empty string, use that exact string without trimming/normalization; if present as null or any non-string type, reject the request before acceptance. This matches the typed source contract (`orderId?: string`) and its valid-input `payload.orderId || cmd.commandId` rule while closing JavaScript truthiness coercions for type-invalid values. The `COMMAND_ACCEPTED.economicOrderId` and `pa2_commands.economic_order_id` MUST both equal the derived value from those exact request bytes; `requestSha256` and the row hash MUST equal SHA-256 of those same bytes. `simulator_request_bytes.orderId` and the parsed `FillReport.orderId` MUST also equal this derived value. The scoped unique index therefore enforces one accepted economic intent per account/generation. An exact request retry with the same command ID/fingerprint returns existing lifecycle state; same economic order ID under a different command or changed request bytes conflicts.

`COMMAND_ACCEPTED` starts a command exactly once. Its exact keys are `acceptedEvidenceSha256`, `amountLamports`, `amountTokenRaw`, `amountUsdMicro`, `commandId`, `commandType`, `configSha256`, `economicOrderId`, `frozenQuoteSha256`, `initiator`, `mint`, `poolId`, `requestSha256`, `reservationCashUsdMicro`, `reservationFeeBufferLamports`, `reservationKind`, `reservationPositionLotId`, `reservationTokenQtyRaw`, `riskPolicySha256`, `seedIdentity`, `side`, `simulatorBuildHash`, `simulatorReportSchema`, and `tokenDecimals`. `pa2_commands` stores the exact canonical request, accepted-evidence, and frozen-quote bytes; the event hashes MUST equal the SHA-256 of those exact row bytes. `amount*` and `reservation*` values are canonical unsigned decimal strings, except nullable `reservationPositionLotId`; `side` is `BUY` or `SELL`; `tokenDecimals` is 0..18; `reservationKind` is `BUY_CASH`, `SELL_POSITION`, or `FEE_BUFFER`. Other identity/type fields are non-empty strings, with `simulatorBuildHash` and all `*Sha256` values exactly 64 lowercase hex characters. In the same transaction, insert exactly one `pa2_commands` row and its one `pa2_reservations` row. The command row's immutable identity, byte/hash columns, amounts, policies, initiator/type/market fields, and accepted account/generation sequence MUST equal the event fields/envelope. The reservation row's kind/cash/lot/token/fee fields and creating generation sequence MUST equal the reservation fields/event sequence. No simulator call may start before this transaction commits.

`COMMAND_REJECTED` is the deterministic pre-simulation terminal transition from ACCEPTED only. Exact keys: `acceptedEventSha256`, `commandId`, `evidenceBytesB64url`, `evidenceSha256`, `rejectionCode`, `terminalResultSha256`. It references the exact accepted event hash; the evidence bytes/hash are exact, and the terminal-result hash MUST equal SHA-256 of the exact canonical `pa2_commands.terminal_result_bytes`. It creates no report or fill and releases the reservation in the same transaction. The command projection becomes `REJECTED`.

`SIMULATED` is the only report-creation transition and is allowed once from ACCEPTED. Exact keys: `acceptedEventSha256`, `commandId`, `commandRequestSha256`, `reportSchema`, `reportSha256`, `reportStatus`, `seedIdentity`, `simulatorBuildHash`, `simulatorRequestSha256`, `telemetrySha256`. It binds the accepted-event hash and request hash, exact simulator request/report/telemetry hashes, report schema, pinned simulator build and seed, and the report status. In the same transaction, insert exactly one `pa2_simulation_reports` row keyed by `(account_id,generation_id,command_id)`. Recompute the three SHA-256 values from the exact BLOB bytes in that row; every byte/hash/schema/build/seed column MUST match the event and accepted command. Strictly parse `report_bytes` using the exact versioned `FillReport` persistence shape above; its embedded `status` MUST equal `reportStatus`, and its `orderId` MUST equal the derived `economicOrderId`. The report row's `report_schema`, `simulator_build_hash`, `seed_identity` and `recorded_at_ms` MUST equal the event's `reportSchema`, `simulatorBuildHash`, `seedIdentity` and envelope `recorded_at_ms`; schema/build/seed must also match the corresponding ACCEPTED event and generation-pinned context. These provenance values are not fabricated report object fields. `simulator_request_sha256` must equal the SHA-256 of canonical simulator-request bytes, whose orderId must equal the same economic ID. There is no independent status column to trust: the event, row metadata and parsed report bytes must all agree. The command row state becomes `SIMULATED`. A second report or a byte-different retry is a conflict; the verifier never calls the simulator.

`SETTLEMENT` is terminal and allowed only from SIMULATED when strict parsing of the exact report BLOB yields `status='FILLED'`. The parsed status, `SIMULATED.reportStatus`, `pa2_simulation_reports.report_schema`, `simulator_build_hash`, `seed_identity`, `recorded_at_ms`, and command/economic order identity must all agree with the SIMULATED event, ACCEPTED context and report row; any missing, malformed or conflicting value blocks settlement. Exact keys: `commandId`, `fillRefs`, `reportSha256`, `simulatedEventSha256`, `terminalResultSha256`. `fillRefs` is a non-empty ordered array of exact `{fillId,fillOrdinal}` objects with unique UUID `fillId`s and unique contiguous ordinals beginning at zero. The report and simulated-event hashes MUST equal the sole preceding `SIMULATED` event and its report row. In the same transaction, insert exactly the referenced `pa2_fills` rows, each with matching account/generation/command IDs, fill ID/ordinal, and `report_sha256`; the refs MUST equal the complete set of rows for this command, with no orphan or unreferenced fill. The terminal-result hash MUST equal SHA-256 of exact canonical `pa2_commands.terminal_result_bytes`. Consume the reservation atomically and set the derived command state to `SETTLED`. This lifecycle contract verifies identities, sequence, report/fill linkage and terminal-result commitment only. A lifecycle-only verifier MUST NOT certify fill economics, cash/token balances, P&L, lots, reservations' monetary effects, or any accounting projection; those require a separate accounting fold.

`SIMULATION_REJECTED` is terminal and allowed only from SIMULATED when the bound report status is REJECTED or EXPIRED. Exact keys: `commandId`, `rejectionCode`, `reportSha256`, `reportStatus`, `simulatedEventSha256`, `terminalResultSha256`. Both hashes/status MUST match the sole exact preceding SIMULATED event and report row. It creates no fills; the terminal-result hash MUST match exact canonical command-row terminal-result bytes; it releases the reservation atomically and sets derived command state `REJECTED`. It cannot replace a FILLED report or settle it later.

`COMMAND_CANCELLED_BEFORE_SIMULATION` is terminal and allowed only from ACCEPTED when proof establishes that simulator invocation never began. Exact keys: `acceptedEventSha256`, `cancellationId`, `commandId`, `proofBytesB64url`, `proofSha256`, `terminalResultSha256`. The accepted hash must match. The proof is canonical evidence with its exact byte hash; the verifier MUST confirm there is no report row or fill row for the command. If invocation may have started, cancellation is forbidden and the command must enter `SIMULATION_OUTCOME_UNRESOLVED` instead. This ordinary pre-simulation cancellation creates no report/fill, releases the reservation atomically, requires the terminal-result hash to match exact canonical command-row terminal-result bytes, and sets derived state `CANCELLED_BEFORE_SIMULATION`.

`SIMULATION_OUTCOME_UNRESOLVED` is a terminal automatic-replay hold allowed only from ACCEPTED, when simulator invocation may have started but no exact durable report transition can be established. Exact keys: `acceptedEventSha256`, `commandId`, `errorClass`, `lastLifecycle`, `processIdentity`, `uncertaintyBoundary`, `workerIdentity`. Require `lastLifecycle='ACCEPTED'` and `uncertaintyBoundary='SIMULATOR_INVOCATION_OR_REPORT_COMMIT_UNKNOWN'`; no report hash, report row, fill row, settlement, or report commit may be inferred. Before appending, reread and validate the exact journal and confirm there is no `SIMULATED`, report, settlement, or fill for this command. If exact state cannot be read or contradicts these requirements, retain a process-local hold and append nothing. Settlement is a single atomic transaction from an already durable `SIMULATED` report; ambiguous settlement acknowledgment is resolved by exact readback of that transaction, otherwise the process remains held. It MUST NOT create a `SIMULATED`-origin unresolved event. Identity/error fields are non-empty diagnostic strings. The reservation is retained as `UNRESOLVED_HOLD`; the command row state becomes `UNRESOLVED`. There may be only one unresolved event per command, and no automated event can return it to ACCEPTED, SIMULATED, SETTLED, REJECTED, or CANCELLED.

`COMMAND_MANUALLY_RESOLVED` is terminal and allowed only after an ACCEPTED-origin `SIMULATION_OUTCOME_UNRESOLVED`. Exact keys: `commandId`, `disposition`, `evidenceBytesB64url`, `evidenceSha256`, `operatorId`, `resolutionId`, `reviewerId`, `terminalResultSha256`, `unresolvedEventSha256`. Operator and reviewer are non-empty, distinct identities; the resolution ID is a UUID; evidence hash covers exact canonical bytes; the unresolved hash must identify the unique prior unresolved event. `disposition` is exactly `CANCEL_NO_FILL`. Evidence must prove no simulator effect and no report/fill exists; verifier independently confirms absence of report and fill rows. This event records an operator-reviewed terminal disposition only: it cannot establish a simulator result, adopt reports/fills, synthesize settlement, change accounting, or release the reservation. The terminal-result hash equals SHA-256 of exact canonical command-row terminal-result bytes and sets derived state `MANUALLY_RESOLVED`; the reservation remains `UNRESOLVED_HOLD` indefinitely pending a separately reviewed accounting repair protocol. If absence/no-effect cannot be proven, do not append this event; retain the process-local hold.

The lifecycle fold keys commands by `(account_id,generation_id,command_id)`, checks `command_id`/payload identity on every listed event, requires exactly one accepted event before any successor, validates the exact predecessor hash links above, and rejects duplicate, skipped, reordered, conflicting, or post-terminal transitions. `COMMAND_REJECTED` is distinct from post-report `SIMULATION_REJECTED`; `COMMAND_REJECTED` is legal only before SIMULATED and requires no report/fill row. `COMMAND_REJECTED`, `SIMULATION_REJECTED`, `SETTLEMENT`, `COMMAND_CANCELLED_BEFORE_SIMULATION`, and `COMMAND_MANUALLY_RESOLVED` are terminal. An exact API retry returns the previously stored exact terminal bytes/state without appending another event; changed request bytes under an existing command ID are a conflict. For every account/generation, no command, reservation, report, or fill may be orphaned in either direction: each `pa2_commands` row has exactly one ACCEPTED event; each ACCEPTED event has exactly one command and reservation row; each reservation belongs to that command and matches its creation sequence; each SIMULATED event has exactly one report row and each report row has exactly one SIMULATED event; a report is forbidden without SIMULATED; each SETTLEMENT ref has exactly one matching fill row and each fill row is referenced by exactly one SETTLEMENT; no other command state may carry fill rows. A cancel-before-simulation command MUST have no report/fills. A manually resolved command MUST have no report/fills and retains its unresolved reservation as `UNRESOLVED_HOLD`. `pa2_commands.command_state` is a derived index and MUST equal the fold result, never supply it. Its terminal-result BLOB/hash is compared with the event-bound digest. Reservation states are `OPEN` after ACCEPTED, `RELEASED` after COMMAND_REJECTED, SIMULATION_REJECTED, or COMMAND_CANCELLED_BEFORE_SIMULATION, `CONSUMED` after SETTLEMENT, and remain `UNRESOLVED_HOLD` after SIMULATION_OUTCOME_UNRESOLVED and COMMAND_MANUALLY_RESOLVED. Non-lifecycle events MUST have `pa2_events.command_id IS NULL`; lifecycle events MUST have it non-NULL and equal to `payload.commandId`. Unknown event types or payload versions remain unsupported and hold the fold; they are never treated as no-ops that permit command recovery. This subfold is read-only and structural/lifecycle-consistency only: it does not verify simulator invocation evidence, authorization, accounting, settlement economics, admission, owner readiness, or risk release, and always returns `held=true`, `semanticsVerified=false`, `admissionEligible=false`.

## 6. Exact units, quotes, fees and conservation

- SOL is integer lamports, 1 SOL = 1,000,000,000 lamports. SPL quantity is raw base units. Solana wire-level `Mint.decimals` is `u8` ([official token documentation](https://solana.com/docs/tokens)), while this gateway currently accepts only 0..18 (`src/command-gateway.ts`, `handleSubmitOrder`, current validation near line 637); preserve that app-level range unless separately reviewed. Never infer decimals on restore. Reducer/settlement uses integer raw units and BigInt rational scaling (for example, bounded `10n ** BigInt(decimals)` where a scale is required), never floating-point `10 ** decimals`.
- Account money is signed integer USD micro-units (1 USD = 1,000,000 micro-USD). Token prices are integer micro-USD per token or a versioned rational. SOL/USD is integer micro-USD per SOL. Every field/event includes its unit.
- Canonical integers have no leading zero except `0`, no plus sign, and no negative zero. BigInt handles arithmetic and bounds before storage.
- Preserve legacy accepted decimal lexemes by converting finite JS numbers through `Number.toString()` to an exact decimal rational and recording the conversion policy. Future request interfaces should accept decimal strings. No float arithmetic in canonical settlement.
- Pin rounding policy per generation and field. Buy: derive `input_lamports = floor(reserved_usd_micro * 1e9 / bound_quote_micro_usd_per_sol)`, then book principal cash debit as `floor(input_lamports * bound_quote_micro_usd_per_sol / 1e9)` USD-micro. Persist the numerator, denominator, quotient and remainder for both conversions; require principal debit <= reserved USD-micro and release the unused reservation residual on settlement. Basis is this exact booked principal debit plus only externally debited simulated fees. Keep the current Gateway behavior (debiting requested `effectiveUsdAmount`) as a differential fixture; do not silently revalue it into canonical settlement. Sell: derive gross proceeds from the report output lamports using `floor(output_lamports * bound_quote_micro_usd_per_sol / 1e9)`; never use the mutable SOL/USD cache. Convert each distinct external exit fee component to USD-micro with ceiling; allocate closed token quantity from the reserved lot and close basis by floor of `remaining_basis * sold_qty / remaining_qty`, except final close consumes all remaining basis. Realized P&L is `gross_proceeds - external_exit_fees - closed_basis`; cash delta is `gross_proceeds - external_exit_fees`. Persist each numerator, denominator, quotient, remainder and rounding direction. Reject overflow, negative fee/net proceeds, or conservation mismatch; never hide residuals in floating point.
- Given `usd_micro` and `sol_usd_micro_per_sol`, lamports = `floor(usd_micro * 1_000_000_000 / sol_usd_micro_per_sol)`. Fee conversion = `ceil(fee_lamports * sol_usd_micro_per_sol / 1_000_000_000)` micro-USD.
- Each accepted command binds one immutable quote: SOL/USD value/scale, observed time, source/provider/evidence ID/hash, and market quote value/time/hash, mint/pool/slot if available. Use the exact same bound quote for amount conversion, pool calibration, priority/tip conversion, all fees, proceeds and settlement. A later `updateSolPriceUsd()` cannot change it.
- The current simulator applies `FEE_BPS = 25` to effective swap input while retaining full input in the pool (`src/execution-engine.ts`, constant-product swap calculation near line 62); its price impact is already reflected in modeled output. Record this AMM fee only as attribution included in swap input/output: never debit it again from cash/basis or subtract it again from proceeds. Only separately specified externally debited modeled priority/tip/base components affect cash and P&L. `FillReport` currently exposes priority fee and Jito tip but no base-fee, compute-unit price/limit, or explicit AMM-fee fields; these values are simulated assumptions, never actual chain fees. The simulator fee model (including version/hash, rounding, failure behavior and which external components are modeled or absent) must be pinned in generation genesis and command/report evidence. Solana documents a current base fee of 5,000 lamports per signature and priority fee `ceil(CU price * requested CU limit / 1,000,000)` lamports, charged even when a transaction fails ([official fee structure](https://solana.com/docs/core/fees/fee-structure)). A future chain adapter must separately bind actual transaction/fee evidence and failed-transaction fee semantics; it must not relabel or reuse simulator fields as chain fees.
- Buy basis = exact spend + entry fee. Partial sell closed basis = `floor(remaining_basis * sold_qty_raw / remaining_qty_raw)`; final close receives all remaining basis. Therefore basis is conserved exactly. Realized P&L = rounded-down gross USD proceeds - rounded-up exit fees - exact basis allocated. Match existing metrics: every settled sell increments closed fill; P&L > 0 is a win, <= 0 a loss.
- Conservation: `cash_after = cash_before + settlement_delta`; opened quantity = remaining + closed; opening basis = remaining + closed basis; realized P&L/counters equal folds over fills. Cash/quantity underflow fails closed.

## 7. Atomic command and projection protocol

1. Under the account owner lock, read verified projection and check account/generation/epoch/lease, stop/recovery hold, command/economic IDs, limits, exclusivity, cash, exact lot quantity, policy hashes, evidence and quote freshness.
2. Canonicalize request/evidence with accessors/proxies rejected. Calculate reservation. One `BEGIN IMMEDIATE` transaction appends ACCEPTED, command identity, reservation, event-chain update and checkpoint. Verify affected rows and commit.
3. Only after confirmed commit publish reservation/in-flight projection and invoke simulator exactly once. Unknown commit: do not simulate; reopen/query exact event+command. If existence cannot be proven, freeze admission.
4. On simulator return, canonicalize report/telemetry. One transaction appends SIMULATED, stores exact report bytes/hash, updates command state and checkpoint. Unknown result is reread by command/report hash. Never rerun simulation. If no durable report is proven, mark unresolved and keep reservation.
5. Settle only from the durable report and bound quote. One transaction appends SETTLEMENT, inserts fills, updates cash/lots/basis/fees/P&L/counts, consumes reservation, inserts learning outbox, stores exact response and updates complete checkpoint. Commit before publishing in-memory state or returning success.
6. Lost settlement acknowledgment: query exact command/report/fill key. If matching result exists, return saved response. If verified absent/rollback, retry settlement from saved report only. If unknown/contradictory, block; never duplicate.
7. Failure before simulator invocation can be rejection/cancel only if code proves it never started. After invocation begins without durable exact report, preserve reservation as unresolved. `finally` cannot erase durable risk.

## 8. Risk watermark and emergency stop

Risk consumers read only the last committed, non-unresolved watermark. Compute candidate lastMark/time, peak, lastPeakAt, trough and stop off-state; append the observation and update projection transactionally; await confirmed commit; only then publish. Known precommit failure retains committed memory but places a hold, so neither old stop nor candidate authorizes stop-dependent exits. Unknown outcome freezes and rereads event/hash/version. If any current path may have exposed a candidate, mark unresolved; never use a lower prior stop until exact proof or explicit conservative repair.

On restore, marks are historical and stale. Retain peak/trough/stop, but require fresh identity-matched evidence for market-dependent exit. Source sequence must increase for equal times; different sources with equal times are ambiguous. Stale/future/missing/nonfinite/wrong mint-pool/out-of-order marks cannot update or authorize. Test process death on precommit and unknown commit with lower saved stop.

`EmergencyStopStore` is a second durable resource, not atomically coupled to SQLite. Startup validates/loads it and latches denial before account readiness, listener, or automation. Effective stop = DB latch OR file latch OR unknown/mismatched state. Latch persists deny intent first; failures keep memory latch. Clear requires explicit confirmation, exact stop identity and recovered account READY; cross-store clear must remain fail-closed after crashes. `CLEAR_EMERGENCY_STOP` cannot clear recovery hold or unresolved watermark.

## 9. Migration: current v1 and inert marker v2 to canonical model v2 / SQLite version 3

Known source inputs are (a) a virgin SQLite database with `user_version=0` and zero user-defined schema objects; (b) exact Stage 1 canonical `user_version=1`; (c) exact current inert marker schema `user_version=2` with exactly one `paper_kernel_prototype_marker` row `(singleton=1, marker_version=2, purpose=NONCANONICAL_OFFLINE_PROTOTYPE)`; or (d) exact canonical `user_version=3`. Unknown versions, a nonempty v0 database, altered SQL/trigger/index, unexpected marker data, or mixed layouts refuse without WAL setup or mutation.

1. Inspect linked `sqlite_version()` before migration. Require upstream 3.51.3+, official patched 3.44.6/3.50.7, or exact documented/verified vendor backport of the WAL-reset fix ([official SQLite WAL documentation](https://www.sqlite.org/wal.html#the_wal_reset_bug)). Prior local inspection recorded 3.53.4; deployment checks its actual runtime. This software gate does not prove VFS or power-loss durability.
2. Before changing journal mode, verify the exact source class. For v0 require exactly zero user-defined schema objects (ignore SQLite internal objects only); a v0 file containing any user table, view, trigger or index is not virgin and refuses. For v1/v2/v3 verify every canonical object/trigger/index, integrity/FKs and marker data. Mismatch refuses untouched. Legacy worker must not auto-upgrade canonical DB or open unknown v3.
3. Only after source validation set and read back WAL, `synchronous=FULL`, foreign keys and busy timeout. Refuse if unavailable. WAL is local-host only.
4. In one `BEGIN IMMEDIATE`, create all `pa2_*` tables/indexes/checks/triggers; insert no account/generation; preserve v1 tables/rows byte-for-byte; if source is marker-v2, drop only the exact verified marker table and its sole exact marker row; write migration metadata; set `PRAGMA user_version=3` last; verify exact target SQL/integrity/FKs and empty account/generation tables; commit. For a virgin v0 file, this same atomic transaction creates the complete canonical v3 schema and metadata, with zero account/generation/owner and no capital or genesis.
5. Close/reopen with a fresh worker; recheck actual SQLite version, exact v3 schema, integrity/FKs and durability. Canonical v3 verification also checks empty migrated account/generation state and, whenever records exist, both contiguous sequence dimensions, the single account-global hash chain and each generation genesis commitment. Serve nothing before all checks pass. Unknown commit acknowledgment is reread; ambiguity blocks service.
6. Newly provisioned and migrated DBs have zero accounts, generations, owners and active generation. v1 history remains historical/unadopted; no genesis, fill, position, report, quote, watermark or P&L is inferred. Environment capital, `paper.json`, live snapshots and current process are never migration sources.
7. Only a separate explicit operator genesis may create an account. Schema provisioning/migration is not activation or recovery.

### One-time first-genesis bootstrap and activation

A migrated empty database has no active generation or lease, so bootstrap is a narrowly defined exception to ordinary generation-scoped account writes. It is never automatic and cannot use environment capital, v1 rows, `paper.json`, a live snapshot or process memory as genesis. Require explicit operator authorization and a canonical genesis payload with a stable account ID, stable generation ID, and fingerprint covering every genesis field and policy/version hash.

Under the startup OS process lock, perform one `BEGIN IMMEDIATE` transaction. If no account exists, create exactly one account in `BLOCKED` with owner epoch 0 and no lease, and create the single `PENDING` generation with exact immutable canonical genesis bytes/hash. Then append `ACCOUNT_BOOTSTRAPPED` (account sequence 1, generation sequence 1, owner epoch 0) followed by `GENERATION_CREATED` (account sequence 2, generation sequence 2, owner epoch 0) to `pa2_events`; both carry the same stable account/generation scope, and `GENERATION_CREATED` commits to the stored genesis hash. Write the idempotency key/fingerprint in the same transaction. The account/generation rows and both events are indivisible: if any step fails before commit, none are visible; after commit, recovery must verify the complete pair and hashes. Do not set the active-generation pointer, acquire an owner, create command reservations or enable admission. A retry with the same account ID and exact genesis fingerprint returns the existing bootstrap result. Reuse of that account ID with changed genesis bytes/fingerprint is a hard conflict. The unique account identity, serialized immediate transaction and process lock ensure competing bootstrap workers cannot create multiple accounts, generations or owners.

After commit, close/reopen and independently re-read and validate exact genesis bytes/hash, the event chain and empty initial projection while still blocked and without an account-changing lease. The bootstrap store's operator identity string is only an asserted identity; it is not an authorization credential. Production activation requires the independent authorization artifact and verifier contract below.

### Owner acquisition, renewal, release and fencing contract

**Authorization artifact.** Activation authorization is a canonical JCS object with exact keys `action`, `accountId`, `actorId`, `admissionState`, `authorizationId`, `databaseIdentity`, `expiresAtMs`, `generationId`, `genesisSha256`, `issuedAtMs`, `keyId`, `nonce`, `signature`, and `signatureAlgorithm`. `databaseIdentity` names one immutable database-instance lineage in an external registry, bound to an OS identity proof obtained from the opened database/storage handle. It must change on same-host copy, restore, replacement or relocation; host ID alone, a file path, SQLite file hash, environment string or copied database value is insufficient. A provider that cannot distinguish a same-host copy/restore from the original refuses activation. `action` is exactly `ACTIVATE_PAPER_GENERATION`; `signatureAlgorithm` is Ed25519 as specified by [RFC 8032](https://www.rfc-editor.org/info/rfc8032/); `admissionState` is `READY` or `STOPPED`; IDs and hashes must match the pending account/generation; times are safe UTC milliseconds, `issuedAtMs <= clockObservation.wallUnixMs < expiresAtMs`, and `expiresAtMs-issuedAtMs <= 300000`; nonce/authorization ID are unique in the account journal and `activationId` equals `authorizationId`. The RFC defines the signature algorithm; the following is project-specific authorization policy/message framing, not a change to Ed25519: sign `ASCII("SYLPH-PAPER-ACTIVATION-AUTH-V1") || 0x00 || JCS(the exact object with signature omitted)`, then encode the signature as canonical unpadded base64url.

`authorizationSha256` is exactly `lowerhex(SHA256(ASCII("SYLPH-PAPER-ACTIVATION-ENVELOPE-V1") || 0x00 || U32BE(authBytes.length) || authBytes))`, where `authBytes` are the exact full canonical JCS authorization-object UTF-8 bytes including signature. It is distinct from the signed-message preimage. `authorizationVerifierId` is exactly `lowerhex(SHA256(ASCII("SYLPH-PAPER-AUTH-VERIFIER-V1") || 0x00 || U32BE(keysetBytes.length) || keysetBytes || raw32(verifierBuildSha256) || raw32(verifierPolicySha256)))`; `keysetBytes` are exact canonical JCS keyset bytes, and both trailing hashes are decoded 32-byte lowercase SHA-256 digests of the verifier build and verification policy. All integer lengths are unsigned 32-bit big-endian; over-bound data refuses before allocation. No implementation may substitute `JSON.stringify`, omit signature bytes, normalize Unicode, or hash a parsed/reconstructed object.

The signature verifier reads `keyId` only from an operator-provisioned, immutable canonical keyset and validates signature, revocation, actor, action, account/generation/genesis/database-instance identity, target admission state, validity window and nonce before reservation. It must use the clone-resistant storage-instance provider, not trust request/environment/database identity. Host binding alone does not protect against same-host copies; the provider must prove the original instance lineage and issue a distinct identity or refuse copied/restored storage. The operator must separately provision and approve the trust root, keyset lifecycle, and storage-instance attestation source; none is currently specified. Therefore activation cannot be implemented yet, and the document makes no clone-resistance or activation-readiness claim for current code.

**Replay-safe trust-service contract (required before activation).** A transactional authorization service exposes only idempotent `Reserve`, `Commit`, and `Query` in this protocol version and signs every receipt with its independently provisioned service key; there is no `Cancel` operation or `CANCELLED` state. `Reserve` key is `(databaseIdentity, activationId)` and stores the complete request fingerprint `lowerhex(SHA256(ASCII("SYLPH-PAPER-ACTIVATION-REQUEST-V1") || 0x00 || U32BE(reqBytes.length) || reqBytes))`; `reqBytes` are canonical JCS bytes for the exact object `{accountId,activationId,admissionState,authorizationSha256,databaseIdentity,generationId,genesisSha256,projectionSha256}`. Exact repeated reserve returns the same signed `RESERVED` receipt even after the original envelope's expiry; its receipt `statusAtMs` proves it was authorized within the envelope window. Any changed byte/scope under that key conflicts. The identity proof must be from the storage-instance provider and checked by the service so same-host or cross-host copies cannot reuse the authorization; host binding alone is insufficient. A reservation is durable and non-expiring; exact retries query/resume it, and an orphaned reservation may require external manual repair indefinitely. No local timeout, cancellation, or replacement authorization may release or supersede it. `Commit` idempotency key is `(databaseIdentity, activationId, requestFingerprint, prepareEventSha256)`, where `prepareEventSha256` is the exact hash of the committed `ACTIVATION_AUTHORIZATION_RESERVED` journal event. Commit returns a signed `COMMITTED` receipt bound to all four key fields; changed prepare hashes or any changed scope conflict. `Query` takes and proves the same four fields and returns the same durable result. Receipt bytes are canonical JCS and their `serviceReceiptSha256`/`authorizationCommitReceiptSha256` use `SHA256(ASCII("SYLPH-PAPER-AUTH-SERVICE-RECEIPT-V1") || 0x00 || U32BE(receiptBytes.length) || receiptBytes)`.

Protocol ordering is crash-safe: verify authorization; obtain exact RESERVED receipt; then in one SQLite transaction acquire epoch 1, append `OWNER_ACQUIRED` at sequence 3 and `ACTIVATION_AUTHORIZATION_RESERVED` at sequence 4, store full request fingerprint/receipt, set `state_version=4`, and remain BLOCKED/PENDING. After confirmed commit, compute the exact sequence-4 event hash and call idempotent service `Commit` with a clone-resistant storage-agent proof for that hash. Commit's idempotency key includes this `prepareEventSha256`; its signed COMMITTED receipt and all later Query results must carry and match it. Only after that exact receipt is verified may one final SQLite transaction append `GENERATION_ACTIVATED` at sequence 5, store that receipt, set active pointer/generation/admission/checkpoint and `state_version=5`, then publish. If reserve succeeds before DB intent, exact retry resumes; no reservation burns. If DB intent commits but service commit/ack is lost, Query with the exact prepare hash resolves RESERVED/COMMITTED and the same operation resumes. If service is unavailable or identity cannot be proven, remain blocked. If DB activation commit acknowledgment is lost, reopen and verify exact state/receipt before returning.

**Expired prepared activation resume.** If the `OWNER_ACQUIRED` epoch-1 prepared activation lease expires before finalization, startup retains its process-local hold and performs complete read-only verification of the exact BLOCKED/PENDING state, genesis, sequence-4 `ACTIVATION_AUTHORIZATION_RESERVED`, stored fingerprint, exact `prepareEventSha256`, and signed RESERVED receipt. It queries using the exact `(databaseIdentity,activationId,requestFingerprint,prepareEventSha256)` tuple; it never calls a new Reserve or changes scope. A `RESERVED` status is commit-capable only when its signed `statusAtMs` proves the service validated the signature while `issuedAtMs <= statusAtMs < expiresAtMs`; expiration afterward does not revoke that exact durable reservation. `COMMITTED` is acceptable only when its signed receipt carries the same prepare-event hash and all other tuple fields. Unknown, malformed, mismatched, or unavailable status remains process-local held and cannot activate. Reservations do not expire and cannot be canceled in this version; unresolved external reservations can remain blocked pending manual service-side repair under a separately reviewed procedure.

After lease expiry is proven by the synchronized clock and OS lock, one `BEGIN IMMEDIATE` appends `OWNER_FENCED` at account/generation sequence 5/5 with envelope owner epoch 1, immediately followed by `OWNER_ACQUIRED` at 6/6 owner epoch 2, reason `ACTIVATION_RESUME`, same activation ID/fingerprint and same new owner/lease IDs in both events; set `state_version=6`, remain BLOCKED/PENDING, and preserve the original authorization reservation. The new owner queries with the same exact prepare-event hash; if RESERVED, it idempotently calls Commit with a fresh storage-agent proof over that same sequence-4 event/hash; if COMMITTED, it accepts only a receipt bound to that hash. It then appends `GENERATION_ACTIVATED` at sequence 7/7, epoch 2, updates state_version to 7 and performs exact reopen verification. Repeated expiry/resume repeats the FENCED/ACQUIRED pair at the then-current contiguous sequences with exactly epoch+1 and the same activation fingerprint and prepare hash; final activation always uses the next account/generation sequence and current owner epoch. Any changed fingerprint or prepare hash conflicts. Old epoch writers cannot commit after fencing. The service's durable reservation remains valid across auth-envelope expiry, so retries do not consume twice or require a new authorization. If exact receipt/query or clone-resistant database identity cannot be proven, remain blocked indefinitely pending explicit external repair; no local expiry, cancellation, or duplicate reserve fallback exists.

A copied DB has the same authorization bytes but must prove the original immutable database-instance identity to the service; any copied/restored instance must receive a different identity and fails the signed authorization's database scope. Host-bound identity alone cannot distinguish same-host copies. No such database-instance identity provider or transactional trust service currently exists, so this is a future contract only and no current clone-resistance/readiness claim is made.

Service receipt shape is status-dependent exact JCS. Both statuses contain `databaseIdentity`, `keyId`, `operationId`, `requestFingerprint`, `reservationId`, `serviceId`, `signature`, `status`, `statusAtMs`, `version`; `version=1`, `operationId=activationId`, identifiers/fingerprint match the request, `statusAtMs` is safe-integer service UTC time, and the configured service key is Ed25519 with canonical unpadded base64url signature over `ASCII("SYLPH-PAPER-AUTH-SERVICE-RECEIPT-SIG-V1") || 0x00 || JCS(the exact object with signature omitted)`. A `RESERVED` receipt additionally has exactly `prepareEventSha256: null`; a `COMMITTED` receipt instead has exactly `prepareEventSha256` as lowercase 64-character hex equal to the committed sequence-4 event hash. No other status is valid. Receipt digest includes exact full canonical bytes including signature using the service-receipt hash formula above. The storage-agent prepare proof has exact fields `{databaseIdentity,operationId,requestFingerprint,prepareEventSha256,agentKeyId,signature}` and signs `ASCII("SYLPH-PAPER-ACTIVATION-PREPARE-PROOF-V1") || 0x00 || JCS(the exact proof object with signature omitted)`; signature encoding is canonical unpadded base64url, and the service verifies its host-bound agent key before committing. No service/agent keys are specified here; absence or invalid proof blocks activation.

**Acquisition.** Startup holds the same-host OS lock from before DB classification through its active lifetime. It first loads/latches emergency-stop state, then performs a strictly read-only recovery fold: exact schema/runtime; account/generation identity; all events and hash/sequence chains; genesis, reports and snapshots; arithmetic/conservation; command lifecycle; reservations; unresolved outcomes; watermarks; stop-store agreement; simulator state without replay; and fresh evidence rules. Any uncertainty leaves a process-local `RECOVERY_HOLD`, no lease and no admission, with no SQLite mutation. Only a fully clean result may enter the write transaction.

For first explicit-genesis activation, the caller first holds the stop-store serialization lock shared with latch/clear operations and records the exact stop-store hash/epoch observation. After the full read-only gate and trust-service reservation succeed, `BEGIN IMMEDIATE` rechecks the exact blocked epoch-0 account, one pending generation and genesis fingerprint, no owner/lease/active pointer, no prior activation, empty initial projection, unchanged stop observation and exact signed RESERVED receipt/request fingerprint. In one transaction append `OWNER_ACQUIRED` at account/generation sequence 3/3 and `ACTIVATION_AUTHORIZATION_RESERVED` at 4/4, both epoch 1; set owner/lease columns and `state_version=4`. `OWNER_ACQUIRED` has null prior owner/lease, prior epoch 0, new epoch 1, reason `INITIAL_ACTIVATION`, fresh UUID owner/lease IDs, lock identity, clock observation, authorization ID/request fingerprint and expiry `clockObservation.wallUnixMs+leaseDurationMs` from genesis config. Account remains BLOCKED; generation remains PENDING; active pointer is null. Then idempotently commit the reserved authorization at the trust service. Only after receiving/proving its exact signed COMMITTED receipt may a second `BEGIN IMMEDIATE` recheck the same owner/lease/epoch, hold/stop state, reserved receipt, full fingerprint and projection; append `GENERATION_ACTIVATED` at account/generation sequence 5/5 and epoch 1; set active pointer, generation ACTIVE, requested admission, `state_version=5` and checkpoint; and store the exact commit receipt. `activatedAtMs` equals the verified activation clock observation wall time. The final transaction is atomic; close/reopen and verify exact events/receipts/state before publishing. A stop latch ordered before READY prevents it; a later latch immediately blocks admission. If this prepared lease expires, use only the exact `ACTIVATION_RESUME` path above.

`READY` is permitted only if all recovery checks pass, there is no stop latch, no unresolved command/reservation/watermark, fresh decision evidence is available, and authorization names `READY`. If a valid emergency stop is latched, activation may only request `STOPPED`; it cannot clear the stop. An explicit authenticated STOPPED request is also permitted after the integrity fold passes. A recovery hold, malformed or mismatched stop, unresolved state, unknown commit, or failed authorization rejects both choices. `STOPPED` is not command admission and cannot be treated as healthy trading readiness.

For later owner acquisition on an already-active account, first obtain the OS lock, re-run the complete read-only fold, then proceed only if prior ownership is either durably released (owner fields null) or the persisted lease expiry has passed under the clock rules. For an expired lease, one immediate transaction appends `OWNER_FENCED` with envelope epoch equal to old epoch, followed immediately by `OWNER_ACQUIRED` at exactly old epoch + 1. After a prior graceful release, append only `OWNER_ACQUIRED`, with prior owner/lease null and prior epoch equal to the retained account epoch. Persist a fresh owner UUID, lease UUID, process-lock identity and expiry. Only after commit may the new owner write. Admission remains `STOPPED` until a separate recovery-release transition passes its gates. Graceful shutdown appends `OWNER_RELEASED` with the current epoch and clears all lease columns atomically before releasing the OS lock. Epoch never decreases or resets. No lease renewal is allowed during read-only recovery.

**Renewal and clock.** The genesis-hash-committed runtime config pins the full lease/clock policy. In-process renewal compares `clockObservation.wallUnixMs` deltas to `process.hrtime.bigint()` deltas; values outside tolerance, wall rollback, unsynchronized/missing clock evidence, expiry, or an expired lease cause `RECOVERY_HOLD`, not renewal. `OWNER_RENEWED` uses the same owner/lease/epoch/process lock, requires `renewedAtMs > prior lease_renewed_at_ms`, `newLeaseExpiresAtMs > old lease_until_ms`, and `newLeaseExpiresAtMs = renewedAtMs+leaseDurationMs`. Every write transaction also checks `now < lease_until_ms`, the persisted renewal watermark, exact owner/lease/epoch, and current OS lock nonce. It may not resurrect an expired lease. After crash/restart there is no valid monotonic-clock continuity; a synchronized platform clock-health adapter must prove `wallUnixMs-uncertaintyMs >= lease_until_ms`; then validate and fence with a higher epoch. No such adapter is specified today, so takeover remains unimplementable until deployment supplies and reviews it.

**Stale writer and races.** The OS lock provider is not represented by an account-table column. Before every write, the process locally calls `assertOwned` for the exact lock identity; inside that transaction, it checks account owner ID, lease ID, epoch and expiry against the expected values and verifies the fold-derived latest owner event carries the same lock identity. Every report, settlement, risk mark, stop, release and renewal uses this fence before append or projection mutation. A stale worker may finish computation but its transaction fails `PAPER_ACCOUNT_OWNER_FENCED` before changing any row. SQLite serializes contenders; the unique lock plus immediate transaction allows one epoch transition. Stop latch/clear and activation share one stop-store serialization lock; activation rechecks DB stop epoch and exact stop-record hash while holding it through COMMIT, giving those operations a total order. Exact duplicate activation ID + exact authorization/genesis/projection/target fingerprint returns the already committed result after full reopen verification; same ID with any changed field conflicts. A different activation request after activation conflicts and cannot acquire a second initial owner. Unknown commit acknowledgment closes the worker, reopens read-only, and verifies the complete exact event/state/result. If exact committed or exact prior state cannot be proven, remain held; never retry activation blindly.

The activation API and authorization verifier do not exist in the current isolated bootstrap implementation. `ATTESTED_GENESIS`, active-account/snapshot adoption, owner acquisition, lease renewal, activation, release and command admission remain unsupported; this contract is design-only pending independent review.

The previous inert marker is removed only after exact canonical source verification; marker-v2 must contain exactly the one defined table and one defined row, with no additional objects. v1 is not rewritten or dropped. A rollback restores the exact old version/schema; after commit the exact v3 schema is authoritative. A lost commit acknowledgment is resolved by reopen and exact verification.

## 10. Startup, recovery and admission

Startup order: acquire same-host OS process lock and keep it for the full owner lifetime; inspect/open configured DB without changing journal mode; apply runtime SQLite gate; classify exact v0-empty, v1, v2 marker or v3; refuse unknown/nonempty v0 without mutation; provision/migrate verified class; verify durability and reopen; emergency-stop load/latch; verify explicit account identity; run complete read-only recovery fold and all gates before any account lease. Do not acquire or renew a lease during this phase. Any failed/uncertain check sets a process-local deny hold under the retained OS lock, changes no SQLite row/event, and exposes no UI/listener/automation/command surface. The persisted `admission_state` may still read `READY`; it remains non-authoritative until the process recovery hold is clear and all readiness conditions are re-proven. Only a successful fold may proceed to separately reviewed trust-service reservation/owner acquisition and the exact activation/recovery event sequence. Expose surfaces only after commit, close/reopen and exact event/projection/owner/admission/receipt verification. Acquiring a lease is never proof of recovery.

Unknown event/report version, duplicate with changed fingerprint, chain break, hash/projection mismatch, arithmetic violation, orphan reservation/fill, wrong account/generation/owner, lease uncertainty, unreadable stop, stop mismatch, unresolved simulator outcome or unknown watermark sets a process-local recovery hold before owner acquisition and makes no DB mutation. After a valid owner exists, a hold event may be committed only if current event prefix, clock, lock and lease remain fully verified; otherwise retain the process-local hold. Never create an empty replacement generation or apply configured capital to make boot pass.

Readiness exposes `ledgerSchema`, `ledgerIntegrity`, `processRecoveryHold` and reason, account/generation, owner epoch/lease, last event sequence, projection hash, unresolved command count, open reservation count, watermark hold count, emergency-stop state, fresh market evidence, simulator replay policy and admission state. `READY` requires `processRecoveryHold=false`; a DB row saying READY, successful SQLite open, or healthy v1 journal is not persistence READY.
