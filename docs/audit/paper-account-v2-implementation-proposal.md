# Paper account v2 implementation proposal

**Purpose:** reviewable design for isolated Stage 3 work only. This is not an implementation, migration authorization, account-recovery claim, or approval to wire storage into the terminal. No live snapshot or active paper account may be read, imported, or adopted under this proposal. `AGENTS.md` classifies canonical account state and fencing as CRITICAL: authoring Astra work requires an independent Astra review and reproducible verification before any integration or release gate.

## What v1 actually stores

The current isolated Stage 1 implementation is in `src/platform/storage/paper-ledger.ts`, `paper-ledger-worker.ts`, and `paper-ledger-schema.ts`.

- `paper_generations` stores only `(account_id, generation_id, opening_cash_lamports, created_at_ms)`. `create-generation` accepts multiple generations for an account. There is no account row, active-generation pointer, sealed-generation state, operator provenance, owner lease, or fencing epoch.
- `PaperFillInput` / `paper_fills` store command/fill IDs, timestamp, mint, signed cash lamports, signed token raw units, and a simulation report fingerprint/JSON. They do not store token decimals, pool/position identity, explicit side, quote and fee basis, cost basis, or risk policy inputs. Raw token deltas cannot safely reconstruct the complete gateway position model; the generic simulation report is not a typed substitute.
- `paper_command_events` is a command lifecycle journal constrained to `ACCEPTED`, `SIMULATED`, `SETTLED`, `REJECTED`, and `UNRESOLVED`, with uniqueness per command and event type. It is not a general account event stream and contains no mark, peak, trough, stop, or watermark observations.
- `append-fill` checks report identity and appends one fill plus `SETTLED` in a transaction. It does not atomically update cash/positions/performance projections or reservations. Existing idempotency is scoped to account/generation/command or fill keys, not to an account owner epoch.
- Startup accepts only schema versions 0 and 1 (`paper-ledger-worker.ts`). Version 1 is checked against exact canonical SQL and integrity constraints; unknown versions and unversioned nonempty files are rejected. Existing v1 append-only triggers protect its facts.

These facts are also consistent with the recovery boundary in `paper-account-recovery-design.md`: v1 is isolated journal storage, not a durable account projection or recovery-ready ledger. In particular, no deterministic reducer may claim it can restore the complete `GatewayStateSnapshot` from these fills.

## Proposed v2 domain and write sequence

Keep v1 facts immutable. Add a versioned v2 account model with the following logical records; exact columns and canonical SQL require independent review before implementation:

1. **Account control:** stable `account_id`, nullable `active_generation_id`, current `owner_id`, monotonically increasing `owner_epoch`, and lease metadata. An unset active generation is an intentional blocked state, not a cue to choose the newest or first generation.
2. **Generation genesis/control:** immutable generation identity and explicit genesis facts, plus append-only activation/seal history. Reset must seal the prior generation and activate the next generation atomically. Opening cash and operator/reason/time provenance are explicit; process configuration never silently becomes restored cash.
3. **Immutable account events:** unique event ID, account/generation, owner epoch, append sequence, event kind, canonical payload, canonical fingerprint, and event time. Domain events include typed genesis, accepted command/reservation, durable simulator outcome or unresolved classification, settlement, risk-watermark observation/update, and explicitly authorized control transitions. Duplicate ID + identical fingerprint is an exact replay; same ID + different fingerprint is a conflict.
4. **Projection checkpoint:** account/generation, projection version, last event sequence, previous/event-chain hash, canonical state hash, and canonical projection bytes. It is a verified cache of the deterministic fold, never independent authority. Recompute from genesis/events and compare hashes before adopting it.
5. **Ownership fence:** every account-changing transaction supplies account, generation, and owner epoch. Under `BEGIN IMMEDIATE`, verify current active generation, owner identity/epoch and lease; reject stale epochs before writing. Takeover increments the epoch atomically so a paused prior owner cannot commit later. Lease behavior must be tested for pause/resume and clock anomalies. SQLite WAL is local-host only; network filesystems are unsupported.

Use explicit fixed-point units, not floating point. Store lamports and token raw amounts as canonical signed decimal integer strings and do all arithmetic with `BigInt`. Token position identity must include verified decimals and all identity needed by the gateway; reject inconsistent decimals for the same mint/generation. Store USD risk/basis values using a declared integer scale (proposed micro-USD) and bind the quote value, timestamp, source and evidence identity to each event/command that uses it. Scale/conversion version is part of schema/domain metadata. Reject cash or position underflow unless a separately reviewed event semantic expressly permits it.

Reducer order is the immutable append sequence within one fenced generation, never wall-clock sorting. A risk observation carries source identity and observation time/sequence. Duplicate observations are idempotent; older observations remain auditable but cannot replace the current mark. Peak, trough, and protective stop update only monotonically (peak max, trough min, stop max) from validated fresh observations and version-pinned risk rules. A stale, future, ambiguous, or unresolved watermark cannot authorize stop-dependent automation. On transaction uncertainty, freeze admission and dependent decisions, reopen/query by unique event or transaction identity, and keep recovery held unless the exact committed projection is proven.

For each accepted command and settlement, one immediate transaction must append the canonical event(s), update the projection/version/hash, record the idempotent result, and release/update any reservation together. Commit acknowledgment loss is an unknown outcome: reopen and query the stable transaction key; never rerun a simulator or infer rollback from a missing response. Only after confirmed commit and projection verification may a caller publish the new in-memory projection. This remains a storage contract; gateway integration is a later stage.

## v1 migration and startup gates

The proposed v1-to-v2 migration is **additive and non-inferential**. Its startup order is a safety invariant, not an implementation detail:

- Before any schema mutation or WAL-mode setup, inspect the actual `SELECT sqlite_version()` runtime and apply the version gate below, then verify the original v1 schema, append-only triggers, foreign keys, and SQLite integrity using the existing canonical v1 verification path. Reject malformed or unknown schemas without modifying them.
- After v1 verification, establish required durability settings (`journal_mode=WAL`, `synchronous=FULL`, foreign keys and busy timeout) and verify their returned/effective values. If WAL or FULL durability is unavailable, refuse migration/startup without serving account calls.
- Only then, in one `BEGIN IMMEDIATE` transaction, add reviewed v2 tables/indexes/triggers, record a migration marker, set `PRAGMA user_version=2` last, verify the complete canonical v2 schema and integrity inside the transaction, then commit. Any known pre-commit failure rolls back both DDL and version. A lost commit acknowledgment is treated as unknown; reopen, verify v2 durability and inspect exact version/schema before retrying. Do not serve until exact v2 schema, FK/integrity, and durability checks succeed.
- Preserve all v1 rows byte-for-byte. Do not synthesize v2 genesis, settlements, token decimals, position identity, active generation, owner, risk watermarks, or historical quote provenance from v1 fills, generic reports, process snapshots, environment settings, or current capital.
- Migrated accounts begin with `active_generation_id=NULL` and no writer lease. Legacy rows remain historical/unadopted. No account-changing v2 API is admitted until a distinct explicit genesis and fenced generation activation exists. A migration is schema compatibility only; it is not recovery or snapshot adoption.
- Unsupported version, unknown objects, bad triggers, FK/integrity failure, lease/account mismatch, absent active generation, unresolved command, or projection/hash mismatch keeps the account blocked. Never silently downgrade or open v2 with the v1 worker.

### SQLite WAL runtime gate

Before migration or serving a v2 account, inspect the SQLite library actually linked into the running Node process; do not infer it from `engines.node`. Require upstream SQLite **3.51.3 or later**, the official patched backport releases **3.44.6 or 3.50.7**, or a documented and verified vendor backport of the WAL-reset fix. SQLite's official [WAL documentation](https://www.sqlite.org/wal.html#the_wal_reset_bug) says the bug affects versions through 3.51.2 and is fixed in 3.51.3 and later; it lists the 3.44.6 and 3.50.7 backports. The project currently declares `node >=24.0.0`, so that range alone does not pin the bundled SQLite version. Prior local inspection recorded SQLite 3.53.4, which clears this version gate for that inspected environment only; it is not deployment evidence or a runtime pin. Refuse WAL migration/startup on any other older or unknown runtime unless the exact patched vendor build is documented and verified. This gate addresses a SQLite software defect only; it does not prove the host VFS, filesystem, storage device, power-loss behavior, or `fsync`/flush implementation is durable.

## Verification matrix

All tests use disposable database files. Add deterministic failpoints at transaction boundaries and process-level reopen tests; unit-only reducer tests are insufficient.

| Area | Required evidence |
|---|---|
| Exact arithmetic | Very large positive/negative integer-string arithmetic with `BigInt`; canonical encoding; cash/position underflow rejection; no JS floating point in reducer inputs/outputs; decimals/scale mismatch rejection. |
| Event idempotency | Exact event retry returns the original result without a second projection advance; same ID with changed bytes/fingerprint conflicts; commands and fills remain generation/account scoped. |
| Reducer determinism | Same genesis/event sequence always yields byte-identical projection and hashes; projection checkpoint matches full recomputation; changed/missing/reordered event fails verification. |
| Watermark ordering | Duplicate, equal-time, older, future, stale, and out-of-order marks; old mark cannot replace latest mark; peak/trough/stop never regress; unresolved/ambiguous watermark blocks stop-dependent decisions. |
| Fencing | Two workers competing for an account; epoch takeover; paused old owner resumed after takeover; all old-epoch writes rejected; no overlapping active generations. Include heartbeat expiry and clock rollback/anomaly behavior. |
| Transaction/crash behavior | Fail before event insert, between event and projection, before commit, after commit before acknowledgment, worker death/reopen, and retry by transaction key. Either all settlement/event/projection/result/reservation changes exist or none do; unknown outcome freezes until reread. |
| Migration | Valid populated v1 migrates atomically with every row preserved, version 2 and no active generation/owner; injected DDL/version/precommit failure reopens as intact v1; lost acknowledgment is reread; malformed v1, forged trigger, unknown object/version and integrity/FK fault are rejected without schema mutation. |
| Refusal contract | v1 history cannot be used to create v2 positions/genesis; migrated DB cannot accept account writes before explicit genesis/activation; v1 worker refuses v2; bad projection hash and unresolved command keep account blocked. |

## Explicit non-scope and sequencing

This proposal does not change `CommandGateway`, `terminal/server.mjs`, `EmergencyStopStore`, build outputs, the current process, any paper account file, or any live snapshot. It does not activate a generation, adopt prior state, enable automation, certify reconciliation, add signer/broadcast capability, or authorize financial action. It does not claim simulator replay is deterministic; a separate reviewed simulator checkpoint/unknown-outcome policy remains required.

Before implementation, an independent Astra reviewer must accept the domain units, event ordering, ownership/takeover semantics, additive migration refusal boundary, and crash matrix. After that, implement v2 in isolated storage with disposable DBs only; run schema/reducer/migration/crash tests and full recomputation checks; obtain independent code review. Gateway adapter, startup ordering, operator read-model changes, and any active-account adoption are separate critical stages with their own review and explicit operator gate. Until those later stages pass, readiness and persistence claims must remain blocked.
