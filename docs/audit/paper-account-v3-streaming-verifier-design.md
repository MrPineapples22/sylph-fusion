# Paper-account v3 full-history verifier: bounded-memory design

**Status:** design only; no verifier/runtime code changed in this cycle. This document proposes an exact, read-only-main-database verifier that does not impose a history-count cap. It does not authorize recovery, account activation, command admission, accounting, or trading.

## Problem and current implementation

The current command verifier opens one `BEGIN DEFERRED` snapshot and correctly runs BLOB-length preflights before projecting raw BLOB columns. The preflight now uses bounded scalar `.get()` queries. After that, however, `verifyPaperAccountV3CommandLifecycleConsistency()` still calls `.all()` for generations, events, commands, reservations, simulation reports, and fills, then retains `Map`/`Set` structures across those complete histories. It invokes the owner verifier, which calls journal integrity; the journal verifier itself materializes all accounts, generations, and events, builds `eventsByAccount`, `eventsByGeneration`, and event-identity maps, then folds those arrays. The owner subfold separately materializes account and event rows, groups event arrays by account, and retains owner/lease/lock identity sets. Thus changing `.all()` to `.iterate()` in isolation would remove result arrays but would **not** remove the history-sized maps and sets.

Relevant implementation is in [paper-account-v3-command-integrity.ts](../../src/platform/storage/paper-account-v3-command-integrity.ts), [paper-account-v3-integrity.ts](../../src/platform/storage/paper-account-v3-integrity.ts), and [paper-account-v3-owner-integrity.ts](../../src/platform/storage/paper-account-v3-owner-integrity.ts). The exact v3 tables and indexes are in [paper-account-v3-schema.ts](../../src/platform/storage/paper-account-v3-schema.ts). The package engine floor is Node `>=24.0.0` in `package.json`.

The verifier must continue to check every row in one consistent database snapshot, retain all existing cross-links and fail-closed outcomes, and always return held/non-admission status. A count cap would turn a valid older account into an unverifiable one as history grows; silently truncating a stream would be worse because it could omit a conflicting or corrupt tail.

## Exact data access available in v3

`pa2_events` has unique indexes on `(account_id, event_id)`, `(account_id, account_sequence)`, `(account_id, generation_id, generation_sequence)`, and `(account_id, generation_id, event_id)`, plus `pa2_events_command(account_id, generation_id, command_id, account_sequence)`. Event identity is **account-scoped**: the same `event_id` in two different accounts is valid; reuse within one account is invalid. `pa2_commands`, `pa2_simulation_reports`, and `pa2_reservations` each have primary key `(account_id, generation_id, command_id)`. `pa2_fills` has primary key `(account_id, generation_id, fill_id)` and unique index `(account_id, generation_id, command_id, fill_ordinal)`. These keys support ordered journal scans and bounded one-command-at-a-time probes without a schema migration. They do not support reading owner identity uniqueness or every cross-link from a single in-memory pass without retaining history.

Current `EXPLAIN QUERY PLAN` probes against a disposable canonical v3 database showed:

| Access pattern | Observed plan |
| --- | --- |
| Events ordered by account and account sequence | `SCAN pa2_events USING INDEX sqlite_autoindex_pa2_events_2` |
| One command's events ordered by account sequence | `SEARCH pa2_events USING INDEX pa2_events_command (account_id=? AND generation_id=? AND command_id=?)` |
| Commands ordered by scoped command key | `SCAN pa2_commands USING INDEX sqlite_autoindex_pa2_commands_1` |
| One command's fills ordered by ordinal | `SEARCH pa2_fills USING INDEX sqlite_autoindex_pa2_fills_2 (account_id=? AND generation_id=? AND command_id=?)` |

These are observations for the current linked SQLite build, not permanent query-plan guarantees. Release tests must inspect plans on a populated disposable fixture and verify that any plan change preserves result correctness and acceptable resource behavior.

## Recommended verifier architecture

Keep the public result conservative: `held: true`, `admissionEligible: false`, `semanticsVerified: false`, `economicsVerified: false`, and `atomicityVerified: false`. Keep the current one-snapshot boundary and first run exact schema verification plus bounded BLOB-size checks. Then use synchronous `StatementSync.iterate()` for every unbounded row source, and never call `.all()` for account history. Node documents `iterate()` as returning an iterator that yields row objects; it is available since Node 23.4.0 and Node 22.13.0, so it is present throughout this repository's Node `>=24` engine range. The Node 24.21.0 SQLite module is still marked Release Candidate, so the exact deployed Node release remains a tested runtime dependency.

All SQLite calls are synchronous and can stall their calling thread for the full scan. The verifier therefore must own a dedicated worker process/connection, never run on the terminal's main event loop, and use a supervising parent for a hard deadline. A timer inside the same worker is not a cancellation mechanism because the worker cannot service it while blocked in synchronous SQLite. The supervisor may request graceful cancellation first, but it must have a bounded hard-stop path that terminates the dedicated process; termination must close its database handle and release the snapshot before a retry is allowed. Prefer a child process over an in-process Worker for this initial version unless crash tests prove worker termination releases all iterators, connection locks, and scratch resources. Track verifier status externally as incomplete/held until a complete result is received.

**Windows process-tree supervision.** The current Node runner calls `ChildProcess.kill()`, which targets the direct child and cannot establish that descendants have exited. For the Windows verifier deployment, use a small, fixed native supervisor rather than a PowerShell or `taskkill` wrapper as the hard-stop authority. It should create a private Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, apply only the required resource limits, create the worker with `CreateProcessW(CREATE_SUSPENDED)`, assign it to the job, and only then resume its primary thread. Creating the worker suspended closes the race where it could spawn an unsupervised descendant before assignment. Do not enable breakaway; fail closed if the current host's nested-job constraints prevent assignment. On any setup failure, terminate the suspended worker and wait on its process handle until signaled before closing handles. If termination is not confirmed, return no worker result and keep verification held; do not clean its attempt directory or retry. The supervisor must retain the only job handle, avoid inheriting that handle into the worker, and wait for process/job active-count zero before reporting termination or allowing scratch cleanup. Job Objects normally associate processes created by job members with the job, but breakaway flags and processes created through mechanisms outside normal `CreateProcess` inheritance can escape; deployment tests must verify the exact Node child behavior and fail closed if a descendant remains. Closing the supervisor unexpectedly must close the job handle and terminate members; restart/janitor logic must still prove the prior job/process is gone before inspecting or removing its attempt directory. These are documented Windows mechanisms and engineering inferences, not current repository behavior. Node's `detached` option is not a substitute: Node documents different process-group/session semantics, not a kill-on-parent-close job contract. Sources: [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject), [Process creation flags (`CREATE_SUSPENDED`)](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags), [TerminateProcess and waiting for exit](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess), [Node.js v24.21.0 child_process](https://nodejs.org/download/release/v24.21.0/docs/api/child_process.html).

For every prepared statement, exhaust its iterator on success. On early exit/error, call the iterator's `return()` in `finally` when available before attempting transaction cleanup; then `COMMIT` only after every pass and completeness check succeeds, or `ROLLBACK` on failure, and close the dedicated database connection. Node v24.21 exposes `return()` on the iterator in a runtime probe; `StatementSync.close()` is not present in that runtime, so do not rely on it. If rollback or close fails, poison/terminate the worker and discard all partial counters. Never retry on the same uncertain connection or return partial verification as success.

Use multiple ordered passes so the JavaScript verifier carries only local fold state:

1. **Account and genesis inventory.** Stream account and generation identifiers in primary-key order. Use keyed lookups and SQL `NOT EXISTS`/count checks for one-root-per-account, missing generations, missing creation events, parent existence/order, and empty accounts. Do not collect entire account/generation tables. Parse one bounded genesis at a time and retain only the current scope needed for the following ordered event scan; if scope state cannot be reduced further without a history-sized map, use the scratch index described below.
2. **Account-global journal pass.** Stream events ordered by `(account_id, account_sequence)`. Verify contiguous account sequence, `previous_event_sha256`, event/payload hashes, canonical payload bytes, row fields, account scope, account-scoped `(account_id,event_id)` uniqueness (also guaranteed by the canonical schema), the first two zero-epoch bootstrap events, and each event's size/content. Retain only the previous event hash, current account sequence, current root-prefix state, and bounded diagnostic aggregates. Include a fixture proving identical event IDs in different accounts are accepted and duplicate IDs in one account are refused.
3. **Generation-sequence pass.** Independently stream events ordered by `(account_id, generation_id, generation_sequence)`. Verify each generation's sequence starts at 1 and is contiguous. Check the creation-event and bootstrap sequence rules at the first rows of each group. Use SQL joins/anti-joins against `pa2_generations` to prove each generation has exactly one creation event, correct root/parent linkage, and no event references a missing generation. This second pass replaces the current `eventsByGeneration` history arrays.
4. **Owner/fencing subfold.** Stream each account's events in account-sequence order and run the existing OWNER_* state transition checks as a scalar fold. Owner/lease/lock identity non-reuse currently depends on history-sized sets. Keep those identities in a per-verification, disk-backed scratch uniqueness table with composite keys, using a **separate writable SQLite connection to a dedicated scratch database file**. The scratch database is verifier-derived temporary state, not a source of truth; never attach it to or write it through the read-only `main` connection, and never persist/reuse it across verifier calls. This boundary is required: a disposable Node v24.21.0 probe opened `main` with `new DatabaseSync(mainPath, { readOnly: true })`; after `ATTACH DATABASE ':memory:' AS scratch`, both `CREATE TABLE scratch...` and `INSERT INTO scratch...` were rejected (`ERR_SQLITE_ERROR`). The same CREATE/INSERT succeeded on a second writable `DatabaseSync` opened on its own dedicated scratch file while the main handle remained read-only. SHA-256 of the main file was identical before and after both probes. Thus attached/in-connection TEMP storage is not a viable implementation under this runtime/API, even when the attached database itself is in memory.

   Each verifier attempt must create a fresh, exclusive directory beneath a separately provisioned private scratch root. `fs.mkdtemp()` supplies an atomic unique directory name (six random characters in Node v24.21); the name is not the security boundary, so the parent root must prevent other principals from listing, replacing, or redirecting entries. On POSIX, provision the root owner-only (for example `0700`) and verify owner/mode and no symlink path components. On Windows, Node's `mkdtemp` has no security-descriptor parameter, and its `mkdir({mode})` mode bits cannot express the required per-principal DACL: Node documents that only write permission can be changed and owner/group/other distinctions are not implemented. A private root must therefore be provisioned with an explicit DACL using a platform helper/installer (for example Win32 `CreateDirectoryW` with `SECURITY_ATTRIBUTES`) and the effective DACL verified before use. Do not assume `%TEMP%` is private: the inspected machine's temp root had an unprotected inherited DACL with multiple principals. Never create an attempt directory in a permissive temp parent and then try to repair its ACL afterward. Never reuse an attempt path after a crash. Any ACL/ownership/path validation failure aborts and leaves the verifier held.

   Apply explicit scratch database page/cache bounds, monitor per-attempt directory bytes and filesystem free space, and abort on high-water/disk-pressure failure. These observations alone are not a hard per-attempt disk quota; a platform quota or isolated quota-bearing volume may be required. On normal completion, close the scratch connection and remove the attempt database and any `-journal`, `-wal`, and `-shm` sidecars before reporting complete cleanup. The identity-index prototype below uses `journal_mode=MEMORY` for its fixed 256 KiB database and single-row autocommit statements; this is narrowly scoped and not a general verifier database recommendation. Other scratch database modes remain a separately reviewed choice. Never delete the main account database's WAL/SHM files. If deletion fails, report cleanup-incomplete and quarantine the attempt directory; do not treat a later invocation as its owner. A startup janitor may remove leftovers only while holding the exclusive scratch-root lease described below. It must not infer death from age, a PID number, or a pidfile. These controls require platform-specific implementation and review; a dedicated file alone does not establish confidentiality, bounded disk use, or cleanup correctness.

### Isolated per-attempt identity-index prototype

`src/platform/storage/paper-account-v3-scratch-identity-index.ts` adds an isolated helper for bounded point `has`/`remember` operations over `owner`, `lease`, and `lockNonce` namespaces. It is not wired into either integrity verifier, Gateway, startup, ownership, or account recovery, and its result is not a readiness signal. Callers must supply an already-private, fresh, empty attempt directory and an explicit `maxBytes` option; no production default is chosen. The cap must be a 4096-byte page multiple between 8192 bytes and the implementation ceiling of 64 MiB. It rejects a missing, linked, non-directory, nonempty, or previously used path, and exclusively creates `scratch.sqlite` with `open(..., 'wx')`. It exposes no raw `DatabaseSync`, SQL method, or transaction interface. Keys must match the existing canonical lowercase UUID syntax used by `paper-account-v3-owner-integrity.ts` (36 UTF-8 bytes); namespace and key validation occurs before SQL. Each remember is one single-row `INSERT OR IGNORE` autocommit statement. The helper checks live page count and the main database file's logical byte size against the caller's configured cap on open, before/after point operations, and on close. Any SQLite/stat/configuration error poisons/closes the handle and all later calls fail; caller must discard the entire attempt directory and must never reopen it after process death or an operation error.

The prototype enforces and verifies Node's defensive SQLite mode, `page_size=4096`, a per-open `max_page_count=maxBytes/4096`, `journal_mode=MEMORY`, `temp_store=MEMORY`, `cache_size=-1024`, `mmap_size=0`, and connection limits `length=512`, `sqlLength=8192`, `attach=0`. It checks the configured cap before close, runs `integrity_check`, confirms `writable_schema` remains off after an attempted enable (defensive-mode check), and refuses close if configuration, integrity, file-size, or directory-content checks fail. The helper requires the `DatabaseSync.enableDefensive()` and mutable `DatabaseSync.limits` APIs, feature-gating to Node v24.15 or newer and failing closed if the APIs/readbacks are unavailable. A separate Node v24.21.0 / SQLite 3.53.4 disposable raw-SQL probe accepted 55 text values of approximately 3 KiB each, then reported `SQLITE_FULL` (`database or disk is full`) at page_count=max_page_count=64; after the failed insert, `integrity_check` was `ok`, row count stayed at 55, and the only file was `scratch.sqlite` at 262144 bytes. The helper's regression repeats the bounded-growth/failed-insert check using canonical UUID identities and a deliberately small explicit 256 KiB test cap. After close/reopen, SQLite resets the connection's `max_page_count` readback to its default; the oracle therefore checks the resulting page count, exact logical file size, row count, and integrity, while the live helper verifies the actual configured `max_page_count` on its connection. These are local disposable probes, not guarantees across every filesystem/runtime.

SQLite's official documentation says `max_page_count` caps pages in the database file, MEMORY journal mode stores rollback state in volatile RAM, and `temp_store=MEMORY` keeps temporary tables/indexes in memory. The observed fixed main-file bound therefore does not bound directory metadata, filesystem cluster allocation, low-free-space behavior, native/SQLite/Node memory, or an attacker with access to the attempt directory. SQLite's `max_page_count` is a per-connection/per-file control, not a filesystem quota; `maxBytes` is an app-enforced logical-size cap checked around each operation. MEMORY journaling can leave a database corrupt if a process crashes mid-write; crash recovery is deliberately not supported, and a fresh attempt path is required. The host probe found 5,148,921,856 bytes free on C: NTFS and `fsutil quota query C:` was access-denied; CIM quota classes returned no instance, so a per-attempt filesystem quota remains unverified. No free-space reserve or total-process-memory ceiling has been chosen; callers must supply a cap, and deployment must separately justify it from expected identity-history volume. Keep the whole verifier blocked on private-root lifecycle, hard supervisor cancellation/reaping, total process-memory limits, disk reserve/quota policy, and exact supported-runtime/OS validation. This prototype alone does not resolve any of those gates.

Primary references: [Node.js v24.21.0 SQLite API](https://nodejs.org/download/release/v24.21.0/docs/api/sqlite.html) (`enableDefensive()` and mutable `limits`); [SQLite PRAGMA documentation](https://www.sqlite.org/pragma.html) (`max_page_count`, `journal_mode`, `temp_store`, `mmap_size`); and [SQLite defensive configuration](https://www.sqlite.org/c3ref/c_dbconfig_defensive.html).

   Keep every source-of-truth anti-join and cross-link query within the read-only `main` database. SQLite cannot use a normal SQL join/anti-join across the independent scratch connection. The scratch table is only for historical uniqueness keys whose full set cannot be retained in JS. If a future invariant requires comparing streamed `main` keys against scratch keys, use an exact ordered application-level merge (or revise the reviewed architecture); do not assume cross-database SQL visibility. Any scratch I/O, uniqueness constraint, iterator, or cleanup failure aborts verification and leaves the result held. Never substitute an unbounded JavaScript `Set`.
5. **Command lifecycle pass.** Stream `pa2_commands` in primary-key order, processing one command at a time. For each command, query its `pa2_events_command` range in account-sequence order, fetch its one reservation/report row by primary key, and stream its fills in ordinal order. Validate ACCEPTED/SIMULATED/terminal transitions and every existing byte/hash/scope/state link before dropping that command's local state. Process fill references from the one bounded event payload against the fill iterator; do not retain fills for all commands. Use indexed `NOT EXISTS` checks in both directions for commands without ACCEPTED, lifecycle events without command rows, reports without SIMULATED, fills without SETTLEMENT, and reservations without commands. Compare aggregate verified counts with bounded SQL counts so omissions and duplicate processing are detectable.
6. **Result and diagnostics.** Return scalar row/event counts and fixed-size status/hash summaries. Unknown event families remain held/unsupported. Do not return an unbounded list of unique unknown event names: return total unique unsupported type/version count, a deterministic digest over the sorted set, and a small explicitly labeled diagnostic sample with a truncation flag. This bounds response memory without truncating verification or changing the held decision.

The independent scratch-file approach is preferred over keeping identity sets or all command folds in JavaScript. Its memory should be approximately O(B + S + C), where B is the maximum single persisted BLOB (currently 1 MiB), S is one command's bounded event/report/fill-reference working state, and C is configured SQLite cache plus fixed current account/generation fold state. Scratch disk is O(number of identities and any temporary sort/index state), and total work is O(N log N) at worst for indexed lookups, or O(N) for ordered scans plus per-command index ranges. Runtime and scratch-disk limits may abort a verifier run, but must never skip rows or return a clean/ready result.

The long DEFERRED read snapshot also pins a WAL end-mark. SQLite documents that a checkpoint cannot move past pages needed by a live reader and that a long reader can prevent checkpoint progress; WAL growth can degrade read performance and consume disk. Define deployment-configured per-attempt budgets for wall time, WAL bytes/growth, and minimum free-space reserve before implementation. The supervisor records the `-wal` baseline, monitors sidecar size/free space while verification runs, and kills the verifier process if any budget is exceeded. The worker must then close/release its transaction; no partial result is accepted. Do not issue a TRUNCATE/RESTART checkpoint concurrently with the pinned reader. After the reader exits, ordinary/maintenance checkpointing may resume and must check its returned status. Resource budgets abort one verification attempt and preserve `held`; they are not lifetime/history-count caps and must not change event retention or truncate scans.

The scratch contract remains an **implementation blocker** until independent review pins the OS-specific private-directory ACL/permission checks, temp-store/cache behavior, page and disk quotas, supervisor cleanup after process death, and cleanup-failure reporting. The read-only probe resolves only the SQLite connection boundary: scratch writes must use an independent writable connection/file; it does not establish those other guarantees. A strict hard process-memory ceiling cannot be claimed from `iterate()` alone: SQLite page cache, one-row BLOB materialization, canonical parsing, Node object overhead, and VM/runtime overhead remain.

## Alternatives considered

| Approach | Benefit | Limitation / decision |
| --- | --- | --- |
| Replace every `.all()` with `.iterate()` but preserve current maps | Small code diff and lower transient arrays | Still O(history) JavaScript memory; reject as insufficient. |
| Global streaming fold plus JS maps/sets for per-command or owner identities | Simple transition logic | History-sized maps remain; reject as insufficient. |
| Per-command indexed stream plus SQL anti-joins, using a separate writable scratch DB for unique historical identities | Bounded JS state, uses current indexes, validates complete history; preserves read-only `main` connection | Recommended only after private temp-dir, quota, supervisor cleanup, and platform permissions are reviewed and tested. No cross-connection SQL join/anti-join is available; source-table anti-joins stay in `main`, and any scratch comparison must use an exact ordered merge. |
| TEMP table or attached `:memory:` schema on the read-only main connection | Would avoid another file/connection | Rejected by disposable Node v24.21.0 probe: CREATE/INSERT are denied after ATTACH on `DatabaseSync(...,{readOnly:true})`. |
| Giant SQL joins/grouping to validate all lifecycle links | Fewer JS loops | Join multiplication, complex transition legality, and planner-dependent transient b-trees make proof and resource behavior harder. Use SQL for narrow orphan/uniqueness checks, not as the sole ordered lifecycle state machine. |
| LIMIT/OFFSET pages | Fixed page-sized JS buffers | OFFSET grows expensive; pages must remain inside one snapshot. Keyset pagination could work but increases cursor/sequence proof complexity without benefit over `iterate()`. |
| Permanently checkpointed verifier cursor or snapshot | Could reduce repeated work | Not sufficient to verify mutable/tampered prior history without a separately reviewed signed checkpoint trust contract. Out of scope. |

## Evidence collected

A disposable Node `node:sqlite` benchmark created 120,000 rows with 256-byte BLOBs and consumed the same ordered query through `.all()` and `.iterate()` in separate Node processes. It was run with `node --expose-gc C:\Users\juans\AppData\Local\Temp\paper-iterate-bench.mjs <temp-db-path> all` and the same command with `iterate`. Environment: Node v24.21.0, linked SQLite 3.53.4. `.all()` increased RSS from 68.4 MB to 207.7 MB and V8 heap from 4.5 MB to 60.2 MB; `.iterate()` increased RSS from 68.6 MB to 78.4 MB and V8 heap from 4.5 MB to 4.5 MB. Both visited all 120,000 rows and computed the same checksum. This is an illustrative local prototype, not a production capacity benchmark and not proof that every SQLite/query/runtime configuration uses constant memory.

A second disposable WAL probe held a reader's `BEGIN DEFERRED` snapshot after its first `SELECT`, while a writer appended 100 rows of 4 KiB with `wal_autocheckpoint=1`. `PRAGMA wal_checkpoint(PASSIVE)` reported `checkpointed=0` while the read snapshot was pinned; after the reader rolled back, a later PASSIVE checkpoint reported all then-observed frames checkpointed. The frame count depends on the writer transaction/batching pattern and is not a stable benchmark value. In the same Node v24.21.0 process, an unfinished `StatementSync.iterate()` iterator exposed `.return()`, and calling it returned `{done:true}` before rollback; `StatementSync.close` was `undefined`, and the rollback left `db.isTransaction === false`. This confirms the documented WAL pin/cursor cleanup behavior for the local runtime only; it does not establish a safe production WAL budget or worker-kill contract.

A separate disposable read-only/scratch probe used Node v24.21.0 with SQLite 3.53.4. It created a temporary `main.sqlite`, read-only opened it, attached `':memory:' AS scratch`, and observed `CREATE TABLE scratch...` and `INSERT` rejected with `ERR_SQLITE_ERROR`; an attempted insert into `main` was also rejected while the existing row remained readable. It then opened a separate writable `scratch.sqlite` connection and successfully created/inserted one identity row. The main database SHA-256 was `830ef971717dde9b7d497554f7386cf6e8dabaf7f3cf5e112f5788fde24866da` before, after attached-memory attempts, and after the independent scratch write. Disposable files were removed by the probe. This validates the connection-level design choice for this runtime, not platform ACLs, disk quota, crash cleanup, or production isolation.

The supported implementation API and runtime floor were checked against Node's v24.21.0 official SQLite docs. SQLite's official transaction docs state that a read transaction continues seeing the same historic snapshot while other connections commit writes. Its WAL documentation explains that a live read mark can stop a checkpoint and make the WAL grow; official `EXPLAIN QUERY PLAN` and query-planner docs explain index scans/searches and temporary b-tree sorting. Accordingly, query plans, WAL pressure handling, cancellation, and temp-store behavior must be tested on the exact bundled runtime. Sources: [Node.js v24.21.0 `node:sqlite`](https://nodejs.org/download/release/v24.21.0/docs/api/sqlite.html), [SQLite transactions](https://www.sqlite.org/lang_transaction.html), [SQLite Write-Ahead Logging](https://www.sqlite.org/wal.html), [SQLite EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html), and [SQLite query planning](https://www.sqlite.org/queryplanner.html).

## Platform and lifecycle feasibility delta (2026-10-05)

The package declares only `node >=24.0.0` and has no `os` allowlist. The inspected runtime is Windows `win32`, Node v24.21.0, SQLite 3.53.4. The supported deployment OS/filesystem matrix is therefore unspecified; design claims below are proven only for this local Windows/NTFS setup unless a row explicitly cites a platform-independent API contract.

**Private root and attempt directories.** Node v24.21's `fsPromises.mkdtemp()` creates a unique directory by appending six random characters, but it accepts no ACL/security-descriptor argument. Node documents that on Windows only the write permission can be changed and owner/group/other distinctions are not implemented, so mode bits cannot express the required per-principal DACL. Microsoft documents that a directory can be created with an explicit `DirectorySecurity`; that ACL is applied during creation, avoiding an access window, whereas a null security descriptor inherits the parent DACL. The new Windows-only `ensurePaperAccountV3ProtectedScratchRoot()` provider in `src/platform/storage/paper-account-v3-windows-scratch-root.ts` uses the built-in Windows PowerShell 5.1 executable via a bounded, hidden, `shell:false` child runner (`src/platform/storage/bounded-child-process.ts`). Its fixed encoded script creates the stable `%LOCALAPPDATA%\SylphFusion-PaperAccountV3-Scratch` root with a protected DACL, current-user ownership, and exactly three full-control principals: current user, SYSTEM, and Administrators. It verifies the existing root without repairing it, rejects reparse path components, UNC/wrong-volume paths, unexpected owner/DACL/ACE shapes, malformed output, stderr, timeout, and nonzero process results. Inputs are passed through the child environment; no path or user value is interpolated into executable PowerShell source. The Windows integration test uses a disposable LOCALAPPDATA tree, proves Node-created `mkdtemp` children inherit the three ACEs, and verifies a preexisting permissive root is refused without repair. A local Windows 10 host probe ran built-in PowerShell `5.1.19041.6456`; the integration test created and re-opened the root, verified inheritance protection/owner/exact ACE set, then observed the same three ACEs as inherited on a child attempt directory. This provider's implementation still requires independent security review; it is not wired into the verifier, and it does not establish scratch byte quotas, orphan cleanup, a service identity policy, or an OS process supervisor. On POSIX, private-root provisioning remains a separate platform requirement. Do not create an attempt directory in a permissive parent and then repair its ACL afterward. Required platform sources: [Node.js v24.21.0 file system API](https://nodejs.org/download/release/v24.21.0/docs/api/fs.html), [.NET Framework `DirectoryInfo.Create(DirectorySecurity)`](https://learn.microsoft.com/en-us/dotnet/api/system.io.directoryinfo.create?view=netframework-4.7.2), [Microsoft file security and inherited ACLs](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights), and [Microsoft `CreateDirectory`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createdirectory).

**Resolved-volume gate and direct-child limit.** Independent review found that path-root syntax alone accepts mapped drive letters and non-NTFS filesystems. Before provisioning or accepting an existing root, the provider now constructs `.NET DriveInfo` for the resolved `LOCALAPPDATA` volume and requires `DriveType.Fixed` and exact `DriveFormat == NTFS`; inability to query either property fails closed. These values are included in the exact child response and revalidated by the parent decoder. Unit tests reject `Network`/`Removable` drive types and ReFS/exFAT/FAT32/unknown filesystem claims without needing to create a mapped drive; the Windows integration additionally proves the current test volume satisfies the gate. Microsoft documents `DriveType.Fixed` as a fixed disk and `DriveType.Network` as a network drive, and `DriveFormat` reports the filesystem name. This proves the Windows-reported drive class/filesystem, not physical-device provenance or storage durability. The bounded child runner sends termination only to its direct child and waits for its close event; if that is not observed within its termination grace it fails with termination unconfirmed. It does not kill or supervise a process tree. The provider's fixed PowerShell body launches no descendant processes, but this runner is not a verifier supervisor and does not resolve child-orphan cleanup or cancellation of future descendants. Sources: [Microsoft `DriveInfo.DriveType`](https://learn.microsoft.com/en-us/dotnet/api/system.io.driveinfo.drivetype?view=net-10.0), [Microsoft `DriveType` values](https://learn.microsoft.com/en-us/dotnet/api/system.io.drivetype?view=net-10.0), and [Microsoft `DriveInfo.DriveFormat`](https://learn.microsoft.com/en-us/dotnet/api/system.io.driveinfo.driveformat?view=net-10.0).

**Scratch-root ownership lease and crash cleanup.** A PID file, age threshold, or `process.kill(pid, 0)` check is not sufficient proof that a scratch directory is unused; PIDs can be reused and a child can outlive its parent. A testable Node-core candidate is a dedicated `scratch-lock.sqlite` inside the protected root, in rollback-journal (`DELETE`) mode. The verifier process opens it and holds a `BEGIN EXCLUSIVE` transaction for the entire attempt, from stale-directory sweep through scratch cleanup. This is a same-host mutual-exclusion lease over the scratch root only; it is not an account owner lease, and no account state or source database is changed. A janitor must also acquire that lock exclusively before deleting prior attempt directories. If acquisition times out, is busy, or the lock DB schema/runtime is not exact, it must leave every directory untouched and report held. The lock database itself is permanent private control state and is never swept.

   This candidate was exercised on a disposable local file: the lock owner held `BEGIN EXCLUSIVE`; a second Node process could not acquire it (`blockedWhileOwnerHeld=true`). After the owner was terminated with `SIGKILL` and the parent awaited its `exit` event, a third connection successfully acquired and rolled back the exclusive transaction. This demonstrates SQLite lock release after process death on Node v24.21.0/SQLite 3.53.4/Windows local storage. It is not yet a cross-platform guarantee. Before adoption, test the lock DB's canonical schema/bootstrap races, hot rollback-journal recovery, simultaneous janitors, process kill at each initialization/cleanup boundary, and contention on every supported local filesystem. SQLite WAL is unsuitable for this lock file because `BEGIN EXCLUSIVE` is equivalent to IMMEDIATE in WAL mode and does not exclude readers; keep this tiny lock DB in rollback-journal mode. The lock owner must itself be the verifier process (or same-process worker) and all cleanup code must obey this lease.

   If using a child process, it can outlive a crashed parent. The child must retain the scratch-root lease while it is alive; a later verifier must refuse cleanup while the lock is busy. That is safe but can leave verification unavailable indefinitely. Production must either provide a service-level process-tree supervisor that kills/reaps the child after parent failure, or accept a fail-closed operational repair path. Do not remove files while the lease is held, and do not claim crash cleanup availability without testing the selected supervisor. A same-process Worker avoids orphan child processes because process death also tears down its threads, but termination timing is asynchronous and the parent cannot reclaim its resources until the worker's exit is observed.

**Cancellation choice.** The v3 store already creates a persistent `worker_threads.Worker` in [paper-account-v3-store.ts](../../src/platform/storage/paper-account-v3-store.ts) and owns a writable-main connection in [paper-account-v3-worker.ts](../../src/platform/storage/paper-account-v3-worker.ts). Do not reuse that worker for verification: its `DatabaseSync` is writable, and a long synchronous scan would block its message loop and bootstrap operations. A verifier needs its own isolated execution context and `DatabaseSync(mainPath, {readOnly:true})` plus its own writable scratch connection.

   A disposable Node v24.21.0/SQLite 3.53.4 test held a `BEGIN DEFERRED` WAL reader while repeatedly calling `.iterate().next()` on an unbounded recursive CTE. The parent wrote one row; PASSIVE checkpoint observed `{log:1, checkpointed:0}`. Calling `Worker.terminate()` returned after worker exit; a follow-up checkpoint showed the read mark released (`{log:0, checkpointed:0}`). In a direct child-process variant, the parent used `fork()` without a shell, sent `SIGKILL`, awaited the child's `exit`, and then observed `{log:1, checkpointed:1}`. Both approaches released the read snapshot in this probe. This is not proof of native-memory reclamation, a universal stuck-I/O bound, or a production cancellation SLA.

   `Worker.terminate()` is asynchronous and Node specifies that JavaScript execution stops “as soon as possible”; Worker resource limits constrain V8 heap sizes, not the whole parent process, SQLite native/page-cache memory, or external buffers. It keeps memory/process ownership simpler and avoids a child surviving parent death. A direct Node child process gives stronger process-level memory/failure isolation and a killable OS process boundary. Use direct `child_process.fork()`/`spawn(process.execPath, ...)` with `shell:false`, never a shell wrapper; on timeout send termination, then hard kill if needed and await `exit` before retry or cleanup. Node's docs clarify that `subprocess.kill()` returning true means the signal was sent, not that exit completed. On Windows Node maps SIGKILL/SIGTERM to forceful termination; POSIX hard cancellation requires SIGKILL after any grace period. The child must hold the scratch-root lease itself. Given the verifier's synchronous SQLite scan and need for a hard deadline, the child is preferred **only when a process supervisor and lease behavior are in the deployment contract**. Without such supervision, a Worker plus process-level lease is safer for orphan handling, but its termination deadline is not established; leave verifier unavailable rather than claim a hard bound. Sources: [Node.js v24.21.0 worker_threads](https://nodejs.org/download/release/v24.21.0/docs/api/worker_threads.html) and [Node.js v24.21.0 child_process](https://nodejs.org/download/release/v24.21.0/docs/api/child_process.html).

**Disk pressure and enforceable limits.** `fs.statfs()` reports mounted-filesystem capacity/free-block information; it is an observation, not a reservation or a per-attempt quota. The `max_page_count` SQLite limit can cap the scratch database's page count, but does not alone cap rollback journals, directory metadata, other SQLite temp files, or all transient writes. The scratch schema/query plan must avoid sorts/grouping/temp b-trees, use one bounded insert transaction at a time, set a bounded page cache and page count, and verify `EXPLAIN QUERY PLAN` for the actual statements. A supervisor may poll scratch directory bytes and `statfs` free space and kill/abort at a configured high-water mark, but this is best-effort and has a polling/one-statement overshoot window.

   Windows NTFS quotas are per-user/per-volume; they require administrator configuration and do not supply a per-verifier-attempt bound by default. Directory-level NTFS quotas are not a general client feature (Microsoft notes them through File Server Resource Manager). Thus a hard per-attempt disk ceiling needs a separately provisioned quota-bearing filesystem/volume or a platform service/native quota provider. `PRAGMA max_page_count` limits pages in one SQLite database file only; it is not a directory quota. SQLite's transient sort/index files are placed according to its VFS/temporary-file rules, which can select a system temp directory rather than the attempt directory. The verifier should therefore use query plans with no scratch-side sorting/temp b-trees; if a required statement needs such a temp structure, a separately tested SQLite temporary-directory provider is required. Until deployment chooses and tests a hard quota provider—or explicitly accepts a softer monitor plus page cap as sufficient—the disk-bound gate remains unresolved and implementation-blocking. `statfs` failures, low free space, max-page errors, `SQLITE_FULL`, worker kill, or unbounded temp-file evidence always abort verification and preserve held status. Sources: [Node.js `fs.statfs`](https://nodejs.org/download/release/v24.21.0/docs/api/fs.html#fspromisesstatfspath-options), [SQLite `max_page_count` PRAGMA](https://www.sqlite.org/pragma.html#pragma_max_page_count), [SQLite temporary files](https://www.sqlite.org/tempfiles.html), [Microsoft NTFS disk quota limits](https://learn.microsoft.com/en-us/windows/win32/fileio/disk-quota-limits), [Microsoft `fsutil quota`](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/fsutil-quota), and [Microsoft filesystem feature comparison](https://learn.microsoft.com/en-us/windows/win32/fileio/filesystem-functionality-comparison).

## Required tests and rollout gates

- Differentially compare the streamed verifier with the current implementation over generated valid histories and every existing corrupt/tampered fixture; require matching accept/throw outcomes, exact counters, and unsupported-event summaries.
- Prove every event in both sequence orders is visited exactly once; test gaps, reorderings, cross-generation hash continuity, duplicate identities, missing generation roots, and corruption at first/middle/last history positions.
- Verify event ID identity semantics: a reused `event_id` under a different `account_id` is valid, while reuse under the same account (even in another generation) is invalid.
- Test owner reacquire/renew/release/fence rules, duplicate historical owner/lease/nonce identities, and the case where a duplicate occurs only in the oldest row while the tail is valid.
- Test each command lifecycle, all orphan directions, duplicate/missing reservations/reports/fills, wrong scope/sequence/hash, multiple fills, and one malformed oldest or latest command. Include thousands of interleaved command histories to prove per-command state is released.
- Use a concurrent second connection to append between verifier passes. The verifier must consistently see either the pre-write or post-write snapshot, never a mixture; assert the transaction closes on success and every error path.
- Pin a WAL read snapshot while a writer appends enough frames to exceed the configured WAL high-water budget. Assert checkpoint progress is pinned while the reader is active, the supervisor aborts at the configured deadline/space threshold, the worker closes/terminates and releases its read mark, checkpoint progress resumes, and no partial “verified” result escapes. Cover disk-space exhaustion and failed worker termination as held/error states.
- Verify parent/supervisor deadline behavior with a deliberately blocked synchronous iterator; cancellation from an event loop sharing that thread must not be treated as effective. Assert the process-level hard stop releases the connection and transaction before retries.
- Reproduce worker and direct-child cancellation under the exact bundled Node/SQLite and each supported OS: pin a WAL snapshot, append a writer frame, assert checkpoint is pinned, terminate the execution unit, await its actual `exit`, then assert checkpoint can complete before cleanup/retry. Repeat enough cycles to detect retained WAL locks/files; do not infer native-memory reclamation from WAL release. For child mode, prove the child itself holds the scratch-root lock and that parent death does not allow cleanup while the child survives.
- Test protected-root ACL provisioning and verification on Windows (including inherited ACEs, reparse points, ACL denial) and owner/mode/symlink checks on each POSIX filesystem. Verify attempt directory atomic creation occurs beneath a private root and that no ACL repair window exists. The current Windows root-provider test covers exact root owner/DACL, inherited attempt-directory ACEs, refusal without repair of a preexisting permissive root, malformed response rejection, and child timeout/output/nonzero behavior. Independent implementation/security review remains a gate; this test does not resolve quota, supervisor, cleanup, or POSIX platform contracts.
- Test the SQLite scratch-root `BEGIN EXCLUSIVE` lease across processes: concurrent verifier/janitor exclusion, lock acquisition after normal close, crash before/during/after lock initialization, hot-journal recovery, worker termination, child kill, parent death, and inability to acquire. Busy/invalid lease means leave scratch untouched and return held; age/PID alone never authorizes deletion.
- Test hard storage controls under quota exhaustion: SQLite `max_page_count`, one-row autocommit journal upper bound, directory-byte monitoring and `statfs` low-space thresholds. Force a `SQLITE_FULL` during insert and prove no partial verification result escapes. Validate the actual deployment quota provider; if only polling exists, document the bounded overshoot and keep the hard per-attempt quota claim disabled.
- Inject iterator parse errors and `COMMIT`/`ROLLBACK` failures. Iterators must be returned/closed before transaction finalization; rollback or close failure poisons and terminates the worker.
- Instrument the DB adapter to reject `.all()` on every history table and assert no row or payload is silently skipped. Verify scalar anti-join/count queries are themselves bounded and use indexes where expected.
- Add memory-slope tests at several history sizes with repeated bounded BLOB sizes. Track RSS, V8 heap, external Buffer bytes, SQLite cache, and scratch-disk growth separately; the test should show no linear application-heap growth. Include maximum-size BLOBs and worst-case command fill-reference payloads.
- Exercise scratch-file permission denial, disk full, temporary index failure, worker termination, transaction rollback failure, and timeout. Every failure returns an error/held state and does not modify `main`; no partial counts are reported as verification success.
- On each supported OS, verify that the main connection is opened read-only; ATTACH `':memory:'` followed by CREATE/INSERT on that handle fails, while a separate private scratch-file connection can write without changing the main file hash. Verify the scratch directory's effective ACL/mode, unpredictable exclusive creation, quota/high-water behavior, low-free-space refusal, and cleanup of the database and all sidecars. Simulate process death with scratch rows present; the next attempt must use a new directory, and cleanup may occur only after supervisor proof that the prior worker is dead. Scratch cleanup failure must be visible and cannot yield a completed verifier result.
- Instrument the query layer to prove cross-table source checks/anti-joins are entirely on the read-only main connection; reject reliance on SQL joins across independent SQLite connections. For any future identity comparison spanning main and scratch, test an exact ordered merge with duplicate, missing, and interleaved keys.
- Test WAL baseline/high-water accounting under concurrent writer load and different checkpoint outcomes (PASSIVE incomplete, later complete after reader close). Ensure the verifier itself does not request an aggressive checkpoint while holding the snapshot.
- Inspect populated `EXPLAIN QUERY PLAN` output on Node's supported runtime and record SQLite version. Query-plan changes may require tuning, never a weaker correctness check.
- Keep independent Astra review mandatory. Do not connect the verifier to terminal startup, owner acquisition, recovery adoption, command admission, or a readiness/certification claim until a separate canonical projection/recovery implementation and review establishes those contracts.

## Implementation sequence

1. Preserve the accepted full-history verifier as a differential oracle; add a result digest definition for bounded diagnostics.
2. Refactor journal verification to two exact ordered iterator passes, replacing per-account and per-generation arrays with sequence counters and SQL checks.
3. Refactor owner verification into a scalar per-account fold and introduce the separately reviewed ephemeral identity scratch mechanism.
4. Refactor command verification into one-command-at-a-time processing with indexed child scans and SQL orphan checks; preserve the read-only snapshot helper boundary.
5. Add differential, adversarial, concurrency, memory-slope, scratch-failure, and query-plan tests. Benchmark under the actual release bundle and supported OS filesystem.
6. Obtain independent Astra architecture/verification review. Keep the function held/non-admission and unintegrated even after acceptance; runtime use is a separate critical change.
