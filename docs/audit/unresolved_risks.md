## Research cycle 26 — Windows process-tree supervision — research/design only — 2026-10-05

Official Microsoft sources support Windows Job Objects as the candidate process-tree boundary for the synchronous SQLite verifier. The sequence should be CreateProcess suspended → assign to a private job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` → resume; otherwise the worker can spawn an uncontained descendant before assignment. An independent code review of `src/platform/audit/durable-research-spool.ts` found that its current API cannot provide exactly-once audit insertion: replay omits `eventId` when calling `Store.appendAuditEvent()`, so a process crash after SQLite commit but before spool compaction inserts the same observation again on restart. Concurrent replay can dispatch the same head record. Appends are not fsynced before acceptance, torn/corrupt lines are silently discarded, rewrite/unlink failures are swallowed after memory state is advanced, and recovered entries bypass configured bounds and event validation. A partial Engine hook now optionally enqueues rejected writes and exposes spool counters when a caller injects the spool; `drainResearchSpool()` is manual only. The production `new Engine(...)` composition does not construct/pass a spool or schedule replay, and Store still does not receive the event ID for atomic deduplication. Failed spool enqueue results are ignored, so a second loss is not reflected in the capture-loss marker. This partial hook is not durable recovery and must not be presented as such.

The accepted storage contract for a follow-up implementation is narrower and testable: each observation must have a stable ID tied to its source event identity/revision; target persistence must receive that ID and atomically commit the ID plus audit payload in the same SQLite transaction; replay of an already committed identical ID must return success without another audit row, while reuse of an ID with different content must fail closed. The spool may remove an item only after that idempotent commit is acknowledged, and an uncertain acknowledgment must be safe to replay. Enqueue acceptance needs an explicit durability boundary and observable bounded-capacity rejection. Startup recovery must validate the complete record schema and limits, surface corrupt tails rather than silently treating them as absent, and expose pending/rejected/recovery state. Tests must cover crash after target commit before spool cleanup, restart, concurrent drain, torn append, capacity and payload limits, disk-full/compaction failure, and same-ID/different-payload conflict. The existing account-specific `pa2_outbox` is not a substitute because research observations must not mutate paper-account accounting state.

SQLite is already opened with WAL and `synchronous=FULL`; this supports a database-native atomic dedupe/write boundary, but does not decide migration compatibility, audit-retention interaction, or stable identity semantics. In particular, dedupe identity must remain recognized across audit pruning or a delayed spool replay could reinsert a pruned row. Resolve that retention/lifecycle contract before implementation.
