# IPC policy status

The required production-like design is a local named pipe with an explicit DACL, remote-client rejection, first-instance protection, verified caller token, operation-level authorization, request-size limits, strict schemas and replay-resistant durable request IDs. Impersonation and revert failures must fail closed.

The client authenticates the pipe server by obtaining the server PID, opening its process with only `PROCESS_QUERY_LIMITED_INFORMATION`, and checking the process token's user and restricted service SID. The broker therefore replaces its own process-object DACL with explicit full access for SYSTEM, Administrators and its restricted service SID, plus only `PROCESS_QUERY_LIMITED_INFORMATION` for the configured client SID. It grants that client `TOKEN_QUERY` on the broker token object, without token adjustment or duplication rights. These grants permit read-only identity verification and do not allow process-memory, termination, token changes, handle duplication, or DACL changes. Runtime enforcement remains unqualified until the hosted Windows test proves the query succeeds and stronger rights are denied.

The initial preflight may test service identity and file isolation before an IPC adapter exists. Such results will not be described as IPC authorization qualification. Arbitrary SQL, arbitrary paths, direct key extraction, unrestricted database reads and client-supplied authority changes remain forbidden.
